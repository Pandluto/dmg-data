# 文档与证据系统 Spec

**Status:** Accepted
**Scope:** 项目架构文档、来源快照、生成证据、验证入口与历史归档

## Problem Statement

项目同时包含公开数据快照、clean-room 运行时、两条执行链、Calc oracle、前端投影、RIA 调查档案和大量研究历史。若版本号、角色数量、覆盖率、实现结论和开发过程被复制到多份 Markdown，任何一次数据或代码变更都会制造互相冲突的“当前事实”。Agent 随后会从过期文档出发重复研究、误判完成度，甚至用旧结论覆盖真实运行结果。

用户需要的是一套与 DEF 相同气质、但适配本项目证据模型的文档体系：从短入口可以迅速理解全局，从架构页可以定位职责，从 Spec 可以确认要求，从生成证据可以核对当前数字，从维护记录和 Git 可以追溯每次变化，并且冲突会被自动检查而不是依赖记忆。

## Solution

建立一个单向、可验证的文档与证据系统：

1. 每类事实只有一个主要所有者；其他页面只解释或链接，不复制可漂移内容。
2. 公开数据升级被定义为原子事务，版本、逐文件哈希、语料聚合哈希、依赖闭包和缺失项同时固定。
3. 当前统计由生成器从锁、目录和审计 JSON 生成；手工文档不得维护第二份数字。
4. Spec、ADR、架构、证据、测试、研究、指南、维护和档案拥有互斥职责及明确生命周期。
5. 一个统一验收入口检查数据一致性、生成证据新鲜度、文档链接和根回归；跨前端或 RIA 的变更再按验证矩阵扩展。
6. 历史材料完整保留但明确降权，任何仍有效的结论必须先回写当前事实源。

## User Stories

1. 作为开发者，我希望从一个短文档入口判断应该阅读 Spec、架构还是证据，以便不从历史报告开始工作。
2. 作为开发者，我希望每项当前架构事实只有一个主要落点，以便修改时无需猜测还要同步哪些重复页面。
3. 作为开发者，我希望看到明确的文档权威顺序，以便代码、测试、生成报告和文字发生冲突时知道如何裁决。
4. 作为数据维护者，我希望数据升级固定精确版本和资产 revision，以便不同日期的“最新数据”不会混在同一提交中。
5. 作为数据维护者，我希望所有选定 TableCfg 都有逐文件哈希和聚合哈希，以便漏文件、混版或手改能被检测。
6. 作为数据维护者，我希望运行时语料同时覆盖资产索引范围和从角色、武器、天赋、装备递归发现的依赖，以便索引外文件不会静默遗漏。
7. 作为数据维护者，我希望缺失的上游文件被列为明确缺口，以便系统不会用空定义或猜测伪造完整性。
8. 作为引擎开发者，我希望“数据完整”“动作可编译”“机制可执行”和“外部行为精确”分层表述，以便低层通过不会被误写成全角色正确。
9. 作为引擎开发者，我希望双执行链的保证范围继续显式存在，以便固定 oracle 与通用产品链不会被文档合并成不存在的统一实现。
10. 作为前端开发者，我希望 settled report 的权威边界写在架构中，以便 preview 或 UI 状态不能覆盖真实结算。
11. 作为调查者，我希望 RIA 被定义为观察与保存事实的系统，以便记录器不会演变成第二套规则引擎。
12. 作为评审者，我希望当前角色数、审计数量和覆盖率来自自动生成页，以便评审看到的数字与仓库输入一致。
13. 作为评审者，我希望每份 Spec 都包含问题、方案、用户故事、实现决策、测试决策和非目标，以便实现前可以发现遗漏。
14. 作为架构维护者，我希望不可轻易逆转的跨模块选择进入 ADR，以便后续修改必须显式替代旧决策。
15. 作为新接手的 Agent，我希望指南给出确定的读取顺序和更新命令，以便能从大纲快速下钻到细节并复现证据。
16. 作为项目所有者，我希望所有历史改动能通过维护记录、来源锁和 Git 提交追溯，以便文档不会抹平真实演变。
17. 作为项目所有者，我希望过期研究仍可恢复但不参与当前验收，以便保留知识而不污染事实源。
18. 作为 CI 或本地验收者，我希望陈旧证据页、损坏链接、错误哈希和根回归由命令直接失败，以便文档正确性成为可执行约束。
19. 作为维护者，我希望新增角色或数据结构导致生成器失效时得到明确错误和维护记录，以便升级不会以“只是 JSON 变化”被草率合并。
20. 作为维护者，我希望完成一次升级后可以再次运行生成命令得到无差异结果，以便快照是确定的而不是时间依赖产物。

## Implementation Decisions

- 文档分为九类：入口、Spec、架构、ADR、证据、测试、指南、研究、维护/档案。各类只承担自己的事实责任。
- 需求权威由 Active/Accepted Spec 和 Accepted ADR 承担；架构页只描述当前已经存在的系统，不保存待办或阶段口号。
- 机器事实由固定来源、来源锁、运行时输出、fixture 和生成报告承担；人类可读数字由确定性生成器汇总。
- 来源锁使用独立的表语料与运行时语料记录，保存 manifest 哈希、内容聚合哈希、版本、revision、文件数和依赖闭包摘要。
- 运行时同步默认读取本地固定资产索引；只有显式 refresh 操作才允许把“最新上游”变成新的候选快照。
- 来源锁更新重新计算所有已登记来源的大小和 SHA-256，不沿用旧哈希，也不删除第三方参考或 Calc fixture 的既有来源信息。
- 数据一致性检查重新读取逐文件内容，并从当前表与 JSON 再遍历依赖闭包；它不信任生成 manifest 中自报的成功状态。
- 生成证据页不包含当前时间或 Git working-tree 状态，因此相同输入与生成器必然得到字节一致的输出。
- 可漂移统计只允许出现在生成证据和明确标注日期/基线的维护记录中。架构、Spec 与指南通过链接引用它们。
- 历史材料进入 archive 后不再是当前事实源；维护记录必须保存迁移范围、冲突裁决和恢复方式。
- 当前双执行链保持显式，直到一份后续 Spec、ADR 和交叉验证共同批准收敛。
- RIA sink、存储和 API 保持观察性；记录失败不得改变运行时结果，重放也只能调用白名单 adapter。
- 所有文档相对链接、必要入口、Spec 结构和禁止的架构叙事由文档检查器守护。

## Testing Decisions

- 最高且统一的基础测试缝是仓库 `check` 命令：先验证来源与语料一致性，再验证生成证据与 Markdown，最后运行根回归。
- 数据检查测试外部可观察的文件合同：固定版本、逐文件大小/哈希、聚合哈希、索引范围、递归闭包和缺失集合。
- 文档检查测试信息架构合同：必要入口存在、相对链接有效、Spec 必备章节齐全、当前架构不包含阶段日志。
- 生成证据采用“重新渲染并字节比较”，而不是测试模板内部函数；陈旧页面必须给出唯一修复命令。
- 数据版本升级必须重新运行三类 audit、analysis、timing、跨角色 oracle 和根回归；变化按报告 diff 审查，不把数字单调下降/上升视为自动好坏。
- 涉及前端目录、timing 或 settled 投影时，继续使用既有前端完整测试、TypeScript 检查和 Demo production build 作为最高可自动化缝。
- 涉及 RIA 时，继续使用真实 record/replay、Schema、OpenAPI、REST/SSE 与存储恢复合同；不以 mock 日志代替。
- 浏览器可见交互仍需真实页面验收；截图只能附加，不能代替结构化 report 和 execution digest。

## Out of Scope

- 本 Spec 不宣称补齐所有角色机制、空间世界、敌人 AI 或 Calc 未公开语义。
- 本 Spec 不把项目迁移到新的 issue tracker，也不要求每个小修都新建任务文档。
- 本 Spec 不用 Agent 操作说明代替产品/架构事实，也不引入一份会与现有文档重复的总合同。
- 本 Spec 不删除 Git 历史或历史研究正文。
- 本 Spec 不解决 AKE 与 Calc 版本不同，也不把当前数据更新解释为外部行为对拍完成。
