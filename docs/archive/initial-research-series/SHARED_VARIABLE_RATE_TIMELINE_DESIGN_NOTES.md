# 共享变速时间轴设计笔记（持续补充）

> 状态：讨论稿，不是已冻结实现规范。
>
> 用途：持续记录共享时间轴、技能释放、资源门控、连携技与交互设计。后续讨论优先补充本文件；互相矛盾的旧想法不直接删除，而是注明已修订或仍待裁决。
>
> 最近更新：2026-08-25。

## 1. 当前目标

时间轴应同时满足：

1. 技能是否能释放，严格由真实战斗状态和状态机决定；
2. 所有角色共享同一条真实战斗时间；
3. 画布单元格是排布、压缩和交互容器，不是固定的 `0.5 秒`；
4. 尽可能少占单元格，同时尽可能让一个技能拥有一个清晰的主单元格；
5. 同一列对所有角色只有一种时间流速，但一个技能可以跨多列，因此同一技能内部可以经历不同列的不同时间流速；
6. 伤害落点、资源变化、技能光标和连携窗口最终都由真实帧投影到画布，不能反过来用格子猜真实帧。

## 2. 已确认的现有错误

现有预演把技能输入帧直接计算为：

```text
requestedFrame = nodeIndex * 15
```

因此一个终结技真实持续 `1.0s ~ 3.1s` 时，在它右侧紧邻一格放置战技，战技仍会被解释成约 `1.5s` 输入。由于它距离终结技结束超过现有输入排队窗，最终被标为无效。

期望行为：

- 终结技仍保持 `1.0s ~ 3.1s`，不能被后继按钮篡改结束时间；
- 右侧紧邻的战技，其语义开始时间应解析为前一技能的有效占用结束时间，即 `3.1s`；
- 在资源、冷却和其它状态都允许时，它应当成功释放，不应标红；
- 不能仅通过延长输入排队窗修复，因为那会错误表达成“在 1.5s 提前输入并缓存到 3.1s”。

## 3. 时间与显示的基本对象

### 3.1 真实时间始终使用帧

所有技能至少区分：

- `startFrame`：实际开始帧；
- `blockingEndFrame`：阻止该角色发起后继普通动作的结束帧；
- `effectEndFrame`：技能效果结束帧；
- `tailEndFrame`：投射物、延迟伤害、持续结算等尾部事件的最晚帧。

初步建议：同角色排布冲突与“能否接下一技能”优先使用 `blockingEndFrame`，而不是一律使用 `tailEndFrame`。否则一个飞行中的投射物或持续伤害会不合理地占住整条角色轨道。

某些技能是否应由 `effectEndFrame` 占格，仍需按机制分类，不能预先一刀切。

### 3.2 列是共享的时间投影区间

画布由有序列 `C0, C1, ...` 组成。每列固定显示宽度，但可拥有不同的真实时间跨度：

```text
duration(Ci) = deltaTime[i] >= 0
T[i + 1] = T[i] + deltaTime[i]
```

当 `deltaTime[i] > 0` 时，该列内部对所有角色使用同一条线性投影：

```text
x(t) = left(Ci) + (t - T[i]) / deltaTime[i] * width(Ci)
```

这次讨论修订了此前“整个相交技能组只有一个统一斜率”的设想：

- 现在要求的是“每一列内部斜率统一”；
- 不要求一个技能从头到尾只有一个斜率；
- 技能跨列时，每一段分别服从所在列的斜率；
- 同一真实帧在所有角色行上必须对应同一个横坐标。

### 3.3 零时长列

允许 `deltaTime[i] = 0`：

- 它必要地占一个可见单元格；
- 它不推进战斗时间；
- 它不恢复技力、不推进冷却，也不推进任何状态机；
- 它是版面占位与对齐约束，而不是实际等待时间。

零时长列中的伤害点或同帧事件如何选择左边界、中心还是右边界显示，尚待确定，但无论如何不能因此改变事件帧。

## 4. 技能跨列与逐列变速

示例：

- 角色 A 的普攻持续 `4s`；
- 角色 B 的战技持续 `1s`；
- 两者同时开始。

当前希望形成的显示是：

1. 第一列共同走过 `1s`，A 与 B 都占用这一列；
2. B 在第一列结束；
3. A 剩余的 `3s` 继续进入下一列；
4. 第二列可以独自承载这 `3s`，因此第一列和第二列拥有不同的时间流速；
5. A 的同一个普攻跨过两列，也就经历两段不同斜率。

设计原则：

- 优先保证列内所有角色共用同一时间跨度；
- 允许长技能自动产生或占用后续“延续列”；
- 技能图标的主锚点和技能真实时间条应分离：图标可以保留在主单元格，时间条跨越所有实际覆盖的列；
- 技能左右光标使用真实 `startFrame / blockingEndFrame` 投影；视觉留缝只能是绘制效果，不能改变时间边界。

## 5. 列拆分规则仍未冻结

“尽可能少占单元格”与“尽可能让一个技能占一个单元格”之间仍需确定稳定优先级。

目前存在一个需要继续裁决的冲突例：

- 角色 A：`1~3、3~5、5~7` 三个连续技能；
- 角色 C：`1~5.7` 一个长技能。

旧设想允许整个 `1~7` 使用三列，C 在第三列内部的 `5.7s` 结束，留下 `5.7~7` 的可用尾部。

新设想强调每列可独立变速。若每次“当前活跃技能集合发生变化”都拆列，则边界会成为：

```text
1, 3, 5, 5.7, 7
```

这会形成四个时间区间，而不是旧设想的三列。

因此后续必须明确以下二选一或提出新的折中算法：

1. **强事件边界模式**：技能开始/结束强制产生列边界，可解释性最强，但列数更多；
2. **紧凑投影模式**：只由技能主锚点、后继技能和显式等待产生必要列；允许其它技能在列内部结束，列数更少。

在规则冻结前，不能让实现者自行凭感觉选择，否则删除、插入和拖动后会发生不可预测的重排。

## 6. 严格的技能释放与资源门控

### 6.1 技力不足时不得释放

- 候选开始帧的共享技力不足时，技能不能被判定为可释放；
- 不允许仅因为按钮已拖入某格就让运行时静默延后；
- 如果用户坚持安排该技能，排轴上必须出现显式的空白时间或“刻意等待”；
- 等待期间由真实状态机逐帧自然恢复，直到资源门槛满足；
- 技力恢复速度、消费后的恢复延迟、技能期间暂停恢复、返还技力和浮点量化均以运行时为准，不能简单写死成 `(缺口 / 每秒恢复值)`。

### 6.2 同时释放的技能是一个开始批次

若同一列、同一真实开始帧安排两个不同角色的战技，且每个消耗 `100` 共享技力：

- 该开始批次应当要求共享技力至少恢复到 `200`；
- 不能因为代码按角色 ID 排序，造成第一个按钮绿色、第二个按钮红色；
- 初步语义倾向于对同帧开始批次进行原子资源预留或总成本校验；
- 若总成本超过共享池上限，则单纯等待永远无法解决，应要求拆分开始时间；
- 同帧资源返还、技能产出和消费的先后仍需服从真实引擎事件顺序，不能只做总和近似。

个人终结技能量、冷却、连携 pending 等门控应分别检查；共享技力的合批不代表其它资源也合并。

### 6.3 空白列与资源加速显示

“空出一整列”表示画布愿意用一个完整可见列承载一段没有新技能发起的时间：

- 真实世界并没有加速；加速的是这段时间在画布上的压缩显示；
- 列持续时间应取满足下一开始批次所有硬门控所需的最早时间；
- 如果下一批两个战技共需 `200` 技力，该列可以自动给出“等待到共享技力 200”的候选时长；
- 是否必须由用户显式插入，还是可在拖拽失败时一键生成，尚待交互确认。当前倾向于必须显式可见，禁止后台偷偷插入时间。

## 7. “刻意等待”全局工具

> **后续修订：**这里描述的是接入单条角色尾链的“普通等待”。第 18 节的“强制等待列”是另一种节点：它负责封组，两者并存，不能互相降级或共用类型。

### 7.1 工具定位

- 在 A、B、C、D 四名角色之外，提供独立的第五个工具框；
- 工具框中提供黑框白底的“刻意等待”按钮；
- 它不属于任何干员、没有伤害、资源和技能类型；
- 它可以被拖到任意角色行或某个技能之前，成为该位置的排轴约束；
- 它必要地占用一个完整单元格。

第五个框可以在界面上沿用用户熟悉的顺序位置，但数据层不要把它编码成普通技能类型 `E`：当前 `E` 已经表示连携技。它应使用独立的 `TimelineControlNode / WaitNode` 类型，避免进入技能伤害、Buff、技力消费和连携逻辑。

这里的“全局”首先表示工具不归属某名干员；它被放到某条轨道后主要延迟该位置之后的动作。等待期间，别的角色已经开始且尚未结束的技能仍会随全局时间继续推进。

### 7.2 初始零时长

刚放下但尚未配置时：

- 等待时长为 `0`；
- 单元格仍然保留；
- 它可以纯粹用于视觉隔离、补格和对齐；
- 与它同时开始并跨过该位置的长技能不会因此推进任何一帧。

零时长等待虽然在真实时间上没有长度，也必须被持久化和恢复；普通的“清理空列/压紧布局”流程不得擅自删除它。

示例：零时长等待、`1s` 短技能与 `4s` 普攻形成的布局可以包含：

1. 一列 `0s` 的刻意等待占位；
2. 一列 `1s`，短技能与普攻共同推进；
3. 一列 `3s`，普攻走完剩余时间。

### 7.3 双击等待按钮后的候选项

双击已放置的“刻意等待”后，系统应尽可能生成有意义的候选，而不是只提供自由输入。

已提出或可自然推导的候选包括：

1. `0s，仅占位`；
2. `等待至共享技力足够`：按照下一同帧开始批次的总成本计算；
3. `等待至角色 X 当前技能结束`：队伍中每名角色分别给出选项；
4. `等待至技能 Y 结束`：当前相关的每个技能分别给出选项；
5. `补尾对齐`：让下一动作的开始与某技能结束对齐；
6. `补头对齐`：根据下一动作自身持续时间，反推等待时长，使下一动作的结束与目标技能结束对齐；
7. `等待至冷却结束 / 连携可释放 / 个人能量足够`：只有确实可由状态机求得时才出现；
8. `自定义时长`。

候选生成要求：

- 负时长候选直接过滤；
- 同一目标帧的重复候选合并，但保留“为何得到该时间”的说明；
- 每项同时显示等待增量和最终绝对时间；
- 所有自动候选必须通过真实状态机复核，而不是只做表面算术；
- “补头对齐”需要知道等待节点后面具体是哪一个技能，因此等待节点应保存目标动作关系，而不只是一个孤立秒数。

## 8. 放置判定与交互预览

放置不应继续依赖“一条角色行的一个 `nodeIndex` 只能有一个按钮”。新的判定至少需要：

1. 将鼠标所在列映射为候选时间区间或排布位置；
2. 找出该轨道在该列中的可用真实时间段；
3. 根据技能的真实阻塞时长、资源、冷却和状态机生成候选开始帧；
4. 放下前展示幽灵预览：实际开始、实际结束、需要的等待、将合并或新增的列；
5. 严格区分“排布冲突”和“战斗状态不允许”；
6. 若缺少资源，给出“插入刻意等待并等待至…… ”建议，而不是把无效技能悄悄排队；
7. 若存在多个可填空段，应按拖拽位置选择最近候选，并允许用户切换，不应永远偷偷选择第一个空段。

## 9. 伤害落点与光标

- 伤害首先拥有真实 `frame`；
- 再根据该帧所在列的共享投影得到 x；
- 同一帧的 A、B、C、D 角色伤害点必须垂直对齐；
- 禁止继续把每个技能的全部 hit 独立压缩进自己的单元格；
- 一个跨列技能的 hit 可以落在任意覆盖列中；
- 技能左右光标分别投影 `startFrame` 与选定的结束语义；
- 相邻技能若真实首尾相接，它们共享同一个真实边界。视觉间距不得参与命中判定和逆向时间计算。

## 10. 连携技当前结论

现有代码已有连携 pending、触发窗口、冷却、消费策略和释放门控的通用骨架，但当前数据只确认了佩丽卡的一条触发规则。其它角色只有技能时长资料，缺少经过验证的触发条件；预演会把它们标记为 `unverified`。

仍需逆向并立项：

- 各角色连携触发事件与有效窗口；
- 多个连携同时触发时的强制释放顺序；
- 触发归属是事件来源、队友、目标还是其它绑定；
- pending 的覆盖、刷新、选择和消费规则；
- 同帧资源与连携命令的事件优先级。

首期可采用：

- 只对已验证规则给出“可释放”认证；
- 暂不支持手捏连携零点几秒；
- 连携开始帧由已验证触发事件与当前门控确定；
- 连携技能区间跨列时服从每列共享投影；
- 未验证规则必须明确显示“规则待核”，不能伪装成已经严格判断。

## 11. 明确延期但需要预留接口的机制

- 连携 HitStop / 屏幕冻结约 `0.5s`；
- 手捏连携窗口；
- 使用终结技延长连携等待；
- 终结技期间禁止其它干员发起技能；
- 更复杂的局部时钟、时间膨胀和状态机机制。

这些机制本轮可以不实现，但列时长必须来自真实时钟域，不能把“全局时间”“角色局部时间”和“纯显示占位”永远写死成同一个数字。

## 12. 数据结构方向（未冻结）

`nodeIndex` 可以继续作为显示锚点和旧数据迁移信息，但不能继续充当真实开始时间。

动作至少可能需要：

```text
actionId
laneId / characterId
anchorColumnId
predecessorId
startConstraint: absolute | after | align-start | align-end | trigger | after-wait
startFrame (求解结果)
blockingEndFrame (求解结果)
effectEndFrame / tailEndFrame (求解结果)
sameStartCohortId
stableSequence
```

列至少可能需要：

```text
columnId
order
durationFrames
kind: normal | continuation | explicit-wait | zero-time-spacer | recovery-wait
sourceConstraintIds
```

“刻意等待”至少可能需要：

```text
waitId
anchorColumnId
targetActionId
mode: zero | fixed | align-start | align-end | resource-ready | gate-ready
durationFrames
referenceActionId / referenceCharacterId
```

所有 `startFrame`、结束帧、列持续时间和投影坐标应尽量由约束与状态机确定性派生；不要把可重算的显示结果当成唯一事实来源。

## 13. 初步验收样例

1. 终结技 `1.0~3.1s` 后紧邻放战技，战技从 `3.1s` 开始且合法；终结技结束不变。
2. `4s` 普攻与 `1s` 战技同时开始，第一列为 `1s`，普攻剩余 `3s` 进入后续列。
3. 一个技能跨越两列时，两列可拥有不同斜率；同一列内所有角色斜率一致。
4. 同一帧的跨角色伤害落点垂直对齐。
5. 共享技力不足时技能不可释放；插入显式等待后，只在真实状态机确认资源足够时转为可释放。
6. 两个同帧战技各消耗 `100` 时，等待候选应恢复到至少 `200`，并以同一开始批次校验。
7. `0s` 刻意等待占一格但不恢复任何资源、不推进冷却。
8. 正时长刻意等待会推进真实时间；其它正在进行的长技能也随时间继续推进。
9. 双击等待可看到按每名角色、每个相关技能计算的对齐候选以及自定义入口。
10. 已验证连携在触发窗口前后严格失败；未验证连携显示待核而非绿色认证。

## 14. 当前最重要的未决问题

1. 技能结束点应在什么情况下强制拆出新列，什么情况下允许落在列内部？
2. “尽可能少列”和“一个技能一个主格”的优先级与确定性优化规则是什么？
3. 删除一个动作后，后继动作应自动前移压紧，还是保留原绝对时间？
4. 远距离拖到空格表示“仅改变顺序”还是“主动等待”？当前建议用显式刻意等待消除歧义。
5. 技力不足的按钮是否完全禁止落盘，还是允许保留红色草稿？当前倾向于幽灵预览可显示，但正式排轴必须配套显式等待。
6. 零时长列上的同帧事件统一画在列左、列中还是列右？
7. 同帧多技能资源消费是否一律原子全成全败，还是按真实引擎顺序逐个执行并向用户展示顺序？“两个战技先恢复到 200”的需求倾向于至少在规划阶段做原子可行性校验。

## 15. 逻辑风险审查

### 15.1 必须切断“格子决定时间、时间又决定格子”的循环

技能时长决定跨几列，列时长又用于解释技能开始时间；等待时长取决于资源，而资源又取决于此前技能的真实开始时间。如果没有唯一的求解方向，拖入一个按钮就可能反复拆列、合列，甚至得到不同结果。

建议冻结为单向流水线：

```text
用户排轴意图与关系约束
  -> 状态机求出真实 requested/actual frame 与释放结果
  -> 使用真实动作区间生成/调整显示列
  -> 将真实帧投影为 x
```

列宽、按钮 x 和视觉占格绝不能反向成为战斗状态机的事实来源。

**2026-08-25 已澄清：**技能真实时间不随占格数变化。例如 A 的普攻始终是 `0~4s`；即使零时长等待、短技能或其它轨道事件令它横跨两格、三格，变化的也只有显示分段。此项不再是产品语义疑问，而是实现时必须遵守的单向因果约束。

### 15.2 “刻意等待”影响谁，必须显式化

等待工具不属于干员，但它被插到某个技能前面时，至少存在两种不同语义：

1. **轨道等待**：只给目标技能及其后继增加 `after-wait` 约束；其它角色可照常开始动作；
2. **全局空转**：该时间段禁止任何新技能开始，所有后续轨道一起后移。

用户当前描述更接近“无归属的轨道等待”：其它已经开始的长技能继续推进，被等待的技能延后。若另需“一整列所有人都不发起动作”的资源恢复列，应当把它作为明确的全局等待模式，不能由空白外观猜测。

正时长等待会推进全局战斗时钟，因此所有已存在的 Buff、冷却、敌人状态、连携窗口和长技能都会一起变化；它不是只增加技力而不产生其它后果。

**2026-08-25 已澄清：**普通“刻意等待”作为一个无干员归属的可插入节点，连接到某条角色尾链，只约束它后面拼接的动作；不会反向影响前面的动作，也不会凭空锁住其它角色。若未来需要“全队禁止起手”的整列空转，应另设大组分隔/全局等待类型，不能混入普通刻意等待。

### 15.3 同一列不必然等于同一开始帧

在可变斜率列中，一个技能可能在列内部 `5.7s` 开始，另一个技能可能在同列左边界 `5.0s` 开始。因此：

- “同时释放批次”只能按真实 `actualStartFrame` 分组；
- 不能看到两个按钮在同一大格就直接把成本相加；
- 拖拽预览必须显示最终开始光标，避免用户误以为它们同时释放。

### 15.4 规划期原子校验与运行时事件顺序不是一回事

“两个战技各耗 100，先等到 200”可以作为严格、保守的规划规则。但真实引擎可能存在：

- 第一个技能同帧返还技力；
- 消费发生在不同内部帧；
- 同帧命令存在强制先后；
- 普通技力与返还技力在后续能量收益上性质不同。

因此需要两层结论：

1. 规划器先证明整个同帧批次在开始前可行，防止任意排序导致一个绿、一个红；
2. 运行时仍按已验证的稳定顺序逐事件执行，最终数值以运行时为准。

如果未来确认游戏允许依靠同帧返还串联释放，再放宽规划规则；不能预先猜测。

### 15.5 多个门控条件未必存在共同可释放时刻

等待并不总能解决问题。例如：

- 技力在 4 秒后足够；
- 连携窗口在 3 秒后过期；
- 或等待到冷却结束时，某个必要 Buff 已消失。

“等待至可释放”不能简单取各等待时长的最大值，而要计算所有有效时间区间的交集。交集为空时应明确报告“当前排轴下无可行释放时刻”，而不是无限加长等待。

### 15.6 技能结束存在多个口径

“等待到某技能结束”“补头”“补尾”和轨道冲突检查都必须标明使用哪个结束点：

- 可接下一动作的 `blockingEndFrame`；
- 动画/主体结束；
- 效果结束；
- 最后一段伤害或投射物 `tailEndFrame`。

默认候选可以优先使用 `blockingEndFrame`，但菜单应在有差异时明确显示，例如“等到可行动 3.1s”与“等到效果结束 5.7s”。

所有占用区间建议使用半开区间 `[startFrame, endFrame)`：前一技能在 `3.1s` 结束、后一技能在 `3.1s` 开始时不算冲突。

### 15.7 零时长列的时间逆映射不唯一

`0s` 列内每个 x 都对应同一个真实帧，因此不能用普通 `x -> time` 公式处理。必须额外保存：

- 稳定的视觉列顺序；
- 同帧控制节点顺序；
- 同帧真实事件的统一绘制边界。

拖入零时长列时，用户改变的是视觉/关系顺序，不是时间。连续放多个 `0s` 等待可以合法占多格，但不得偷偷推进一帧或改变资源。

### 15.8 “最少列”会有多个同样最优的答案

如果只要求最少列，同一组技能可能有多种列拆分方式。全局重新求最优还会导致：用户只移动一个无关技能，整张图却重新跳位。

除列数外，还需要稳定性规则，例如依次优先：

1. 保留用户显式等待和主锚点；
2. 保留已有列 ID 与边界；
3. 只在新增动作真正越界时局部拆列或追加延续列；
4. 最后才压缩可安全合并的列；
5. 相同结果使用稳定动作顺序决定，不依赖对象遍历或角色 ID 偶然排序。

### 15.9 技能时长可能是状态机结果，不是固定常数

技能分支、打断、形态替换、目标状态、HitStop 和未来的局部时钟都可能改变实际结束帧。列只能基于一次真实预演结果重排，不能只读技能面板上的基础持续时间。

重排可能改变显示，但不得反向修改刚刚求出的真实帧。若用户关系约束因此需要重新求解，应开启一轮有上限、可诊断的重新预演，而不是无声循环到“看起来稳定”。

### 15.10 等待的副作用必须可见

刻意等待可能同时造成：

- 技力恢复；
- 冷却减少；
- 连携窗口过期；
- Buff/异常状态消失；
- 敌人状态改变；
- DPS 分母增长。

等待候选不应只写“+2.5s / 技力够了”，还应提示重要副作用，例如“连携将过期”或“增益将在等待期间结束”。

### 15.11 “不允许释放”与“允许做无效草稿”需要分层

若彻底禁止无效按钮落盘，用户必须先插等待再放技能，严格但操作较重；若允许红色按钮永久存在，又可能违背“严格落实能否释放”。

建议区分：

- 拖拽幽灵/草稿层：可以展示无效方案和失败原因；
- 已确认排轴层：无效技能不能伪装成已释放，必须插入等待、调整顺序或显式保留为“未执行指令”。

这样既不伪造战斗结果，也允许用户探索修改方案。

### 15.12 删除与移动会产生关系悬挂

后继技能可能通过 `after(previous)`，等待节点可能通过 `targetActionId`，连携可能通过 `triggeredBy(hit)` 依赖其它动作。删除或移动被引用动作时必须：

- 展示会受影响的后继；
- 选择确定性的重新接线、转成绝对锚点或一起删除策略；
- 以一次事务重新预演和重排；
- 保证撤销可以完整恢复关系，而不仅恢复按钮 x/y。

### 15.13 同帧顺序必须是正式数据

即使真实时间相同，资源消费、连携消费和状态应用仍可能受顺序影响。需要稳定的 `sameFrameSequence` 或来自引擎的强制顺序；不能继续依赖角色 ID 字典序。

零时长等待只能调整视觉或关系顺序，是否允许它调整真实同帧命令顺序必须另设显式操作，不能暗中混用。

### 15.14 “空白列”里仍可能有正在持续的技能

一列没有新按钮开始，不代表战斗处于完全空闲：长技能、投射物、持续伤害和 Buff 仍可能横跨该列。该列能否恢复技力必须由真实恢复规则判断，不能仅凭视觉上没有新图标就默认恢复。

### 15.15 自动对齐候选需要控制规模和时效

“每个人、每个技能都给一个选项”在长轴上会迅速膨胀，而且很多候选会重复或在上游修改后失效。候选应：

- 默认只列当前时间之后、可达且与目标动作有关的边界；
- 按角色折叠，去重相同帧；
- 标出阻塞结束、效果结束、尾部结束的区别；
- 每次打开菜单实时重算；
- 自定义入口始终保留。

## 16. 大组、并行尾链与占格算法（新提案）

### 16.1 大组不是单队列，而是共享起点的多条并行尾链

一个“大组”包含：

- 一个固定的左侧起始帧 `groupStartFrame`；
- A、B、C、D 最多四条独立角色尾链；
- 每条尾链由技能、刻意等待及其锁定组合按顺序构成；
- 一个随追加动作变化的右侧边界：

```text
groupEndFrame = max(endFrame of every lane tail)
```

大组开头同时放下的不同角色技能，其左光标都等于 `groupStartFrame`。例如 A 普攻与 B 战技同时按下，它们在大组最左侧严格对齐。

它“像队列但不是队列”：

- 每条角色轨道内部是只能向尾部追加的顺序链；
- 四条链彼此并行，并不共享一个串行队头；
- 任一短链都可以在自己的当前尾部继续紧贴技能；
- 新技能开始时间取本角色当前尾链结束时间；
- 新技能若比当前最长链短，就填进现有大组；若更长，就把大组右边界向右推；
- 其它角色前面已经确定的真实技能时间不会被改变。

### 16.2 只允许尾部磁吸追加

在一个既有大组中，普通技能的合法落点原则上只有该角色的链尾：

```text
newSkill.startFrame = laneTail.blockingEndFrame
```

若该帧状态机不允许释放，则不能静默挪到更晚帧；必须先在链尾插入一个显式刻意等待，再把技能拼到等待后面。

为了避免关系断裂：

- 一个节点一旦已有后继，就不能单独从链中间抽走；
- 移动或删除中间节点时，至少要把它及其整个后缀作为一个整体处理；
- 刻意等待与其后第一个技能一旦完成拼接，形成不可中途拆开的 `WaitBundle`；
- 可以删除或移动整个 bundle / 后缀，但不能只把等待从技能前面拔走而保留原来的后继时间；
- 修改等待模式或时长会重新计算该 bundle 及其后续尾链，但不改动它之前的动作。

> **当前决定：**行内 `WaitBundle` 就是普通等待的正式语义。第 18 节的整列强制等待只用于组间封条，不得把普通等待升级成整列或新大组。

### 16.3 刻意等待的两个确定模式

> **当前范围：**以下模式属于普通等待，只修改所在角色的后继尾链；强制等待的整列模式另见第 18 节。

#### A. 独立时段

- 用户指定等待时长；
- 等待本身固定占一个主单元格；
- 后继技能从等待结束帧开始；
- 其它角色已经开始的长技能会跨过该单元格继续推进；
- 该单元格是显式的“硬列”，原则上不因其它角色在内部结束而把等待本身拆成多个格。

#### B. 后继技能末尾对齐

等待必须先知道后继技能及对齐目标。若：

```text
S = 本角色当前尾链结束帧
D = 后继技能的实际阻塞持续时间
T = 选择的目标结束帧
```

则候选等待时长为：

```text
waitDuration = T - S - D
```

- `waitDuration < 0` 时无法仅靠等待完成此次末尾对齐；
- `waitDuration = 0` 时仍保留一个零时长可见格；
- `waitDuration > 0` 时先等待，再释放后继技能，使其右光标与目标 `T` 对齐；
- 若后继技能时长受状态机影响，应以预演得到的实际时长复核，必要时进行有上限的重新求解；
- bundle 一旦拼好，等待和后继技能共同移动，不允许中途拆开。

“等待到所有人当前技能结束”是另一个常用候选：若目的是让后继技能**开始**于当前大组最右端，则等待为：

```text
waitDuration = groupEndFrame - S
```

它与“让后继技能末尾对齐 groupEndFrame”的公式不同，菜单必须分别标注。

### 16.4 水位式占格扫描

显示列可以理解成多条尾链在同一个时间水位上共同向右推进。

基础扫描：

1. 从 `groupStartFrame` 开始，将各角色当前应该开始的链头放入活动集合；
2. 找出下一个需要显示的时间边界；
3. 当前边界到下一边界形成一列，所有仍在进行的技能共同跨过这一列；
4. 到达边界后，完成的节点退出，其同角色后继立即尝试在该帧进入；
5. 未完成的长技能保留剩余时长，继续跨入下一列；
6. 重复直到四条尾链全部完成；最后水位就是 `groupEndFrame`。

普通软边界来源包括：

- 技能主体/阻塞结束；
- 同角色后继技能开始；
- 大组最终最长尾结束。

显式刻意等待是“硬列”：

- `0s` 等待产生一整格零时长列；
- 正时长独立等待用一个格表达完整等待区间；
- 其它技能可以在该硬列内部结束，其光标落在列内部；
- 硬列结束后，被等待的后继技能才能开始；
- 这样能够同时满足“等待单占一格”和“其它技能真实时间不被改写”。

### 16.5 三个基准例子

#### 例 1：只有零时长等待

```text
A: 普攻 [0, 4]
B: 刻意等待 [0, 0]
```

显示：

- 第 1 列：`0s` 等待硬列，A 的普攻穿过这一列但没有推进时间；
- 第 2 列：`0~4s`，A 完成普攻；
- A 跨两格，但真实时间始终为 `0~4s`。

#### 例 2：零时长等待后拼 1 秒技能

```text
A: 普攻 [0, 4]
B: 等待 [0, 0] -> 战技 [0, 1]
```

显示：

- 第 1 列：`0s` 等待；
- 第 2 列：`0~1s`，A 与 B 共同推进；
- 第 3 列：`1~4s`，A 走完剩余 `3s`；
- A 跨三格，时间仍为 `0~4s`。

#### 例 3：等待后让 1 秒技能末尾与 A 对齐

```text
A: 普攻 [0, 4]
B: 等待 [0, 3] -> 战技 [3, 4]
```

显示：

- 第 1 列：`0~3s` 独立等待，A 同时推进；
- 第 2 列：`3~4s`，A 与 B 战技共同结束；
- B 的等待与战技组成锁定 bundle；
- A 仍是 `0~4s`，没有因列宽变化而改变。

### 16.6 追加技能如何改变大组右边界

设当前：

```text
A 尾链结束 = 4s
B 尾链结束 = 1s
groupEndFrame = 4s
```

在 B 后紧贴追加技能：

- 若新技能为 `1~3s`，新 B 尾仍短于 A，大组右边界保持 `4s`；
- 若新技能为 `1~5s`，B 成为最长尾，大组右边界扩展到 `5s`；
- A 的原技能仍保持 `0~4s`，只是新的列分段和右侧留白发生变化。

这就是“谁比谁长”的核心：比较的是每条角色尾链的真实结束帧，而不是按钮数量或按钮像素宽度。

### 16.7 另开大组必须有整列分隔

若动作不再紧贴任何现有角色尾链，而要开始一个新的、独立的同步起点：

- 前一大组与新大组之间必须存在至少一个完整的 `GroupSeparatorColumn`；
- 新大组的所有首发动作重新共享一个左侧起始点；
- 默认可允许分隔列为 `0s`，只提供视觉和拓扑断开；
- 若分隔列承担技力恢复或其它真实等待，则它拥有正持续时间，新大组开始帧相应后移；
- 若没有完整分隔列，落下的动作只能解释为前一大组某条尾链的紧贴后继，不能偷偷生成第三种自由起点。

因此排轴只有两类明确操作：

1. 接到现有大组某条角色尾链；
2. 通过整列分隔后创建新大组。

### 16.8 与严格释放门控的结合

每次某条尾链准备在边界启动后继技能时：

1. 收集该真实帧所有准备开始的技能，形成同帧 cohort；
2. 按状态机检查共享技力、个人能量、冷却、连携窗口与其它门控；
3. 全部满足才正式进入活动集合；
4. 不满足的技能留在草稿预览中，并提示在它前面插入刻意等待；
5. 等待与技能拼成 bundle 后重新扫描该尾链及受影响的后续列；
6. 已在等待之前开始的其它角色技能保持原始真实区间，只重新投影显示。

## 17. 新提案仍需确认的一处细节

“独立时间段的刻意等待单占一格”在本提案中被解释为**硬列**：即使另一个角色技能在等待区间内部结束，也只把该技能右光标画在等待格内部，不拆开等待格。

这能严格满足“等待有自己独立持续时间、单占一格”，但也意味着普通技能结束点不一定总形成列边界。若期望任何技能结束都必须拆列，则刻意等待可能被迫跨多格，与“单占一格”冲突。后续只需确认硬列解释是否正确。

> **后续修订：**“固定整列硬分界”只适用于强制等待。普通等待继续参与组内共享边界扫描：它的真实起止帧可以与其它角色动作共同切列，但不会生成组间分隔列。

## 18. 强制等待列（当前最新方案）

### 18.1 它是一列，不是四个互相独立的等待

界面上提供一个可拖拽的“强制等待列”按钮。放入时间轴后：

- 它横跨 A、B、C、D 全部角色行；
- 每行看起来各有一个空白等待格，因此视觉上像“一组按钮 / 一串强制等待”；
- 数据层只保存一个 `WaitColumn`，不能保存成四个可分别编辑的等待节点；
- 点击、拖动、删除、设置时长时，整列一起响应；
- 它不属于任何角色，也不进入技能伤害、Buff 或连携技类型系统。

建议的数据语义为：

```text
WaitColumn
  id
  previousGroupId
  nextGroupId
  mode: seal-only | fixed-duration | atb-target | next-group-ready
  durationFrames
  targetAtb
  createdOrder
```

### 18.2 两个同时成立的作用

一列强制等待同时承担：

1. **给前一大组盖盖子**：前一组在此结束并被封住，不能再把新技能跨过该列磁吸到前组尾链；
2. **为后一大组等待**：等待列结束后，后一组才允许从新的统一左边界开始。

因此它不仅是装饰空格，而是一个正式的大组分界：

```text
previousGroupEnd
  -> WaitColumn [duration]
  -> nextGroupStart
```

并满足：

```text
nextGroupStartFrame = previousGroupEndFrame + waitDurationFrames
```

编辑等待列只会改变它后面的组，不会反向改写前一组技能的真实时间。

### 18.3 拖拽与吸附

- 强制等待列可以从第五个时间工具框拖到技能时间轴；
- 落下时以整列幽灵预览，不能只显示某一角色行的单格；
- 它应吸附到最近的合法大组分界，而不是切断一个正在释放的技能；
- 若鼠标落在技能条上，系统显示最近的“封住此前大组 / 从此处开启后组”候选边界；
- 确认后，边界后的完整动作后缀归入后一大组，不能留下悬空的前驱/后继关系；
- 如果当前位置无法形成完整空列，应拒绝并说明是哪条技能跨越了候选分界。

这保证“空白列”在阻塞动作维度上确实为空。延迟伤害、飞行投射物或 Buff 尾部可以继续穿过该列，但不能有尚未结束的 `blocking interval` 横跨它。

### 18.4 等待模式

#### A. 只封组

- 等待时长为 `0`；
- 仍然保留一整列可见空格；
- 只切断前后大组的磁吸与移动关系；
- 不推进时间、不恢复技力、不推进冷却。

#### B. 固定时间

- 用户输入固定秒数或帧数；
- 整列只占一个显示列，但该列可代表任意正时长；
- 真实时间、技力、冷却、Buff 和其它状态机正常推进；
- 后一大组整体从等待结束帧开始。

#### C. 等待到指定技力档位

候选可以包括：

- 等待到可释放 `1` 个标准战技；
- 等待到可同时释放 `2` 个标准战技；
- 等待到可同时释放 `3` 个标准战技；
- 或直接显示为共享技力目标 `100 / 200 / 300`（具体档位应读取资源配置，而不是永久写死）。

这里保存的是“目标技力”，不是一次算死的秒数。每次上游排轴发生变化时，状态机重新计算从前组结束帧开始，最早何时达到目标。

若当前技力已经达到目标：

- 等待持续时间自然成为 `0`；
- 等待列仍保留并继续承担封组作用；
- 不需要红叉作废，也不让分组边界消失。

若因为恢复暂停、资源上限或其它机制永远达不到目标，应显示“不可达到”，不能无限延长。

#### D. 等待到后一组可释放

系统读取后一大组首发同帧 cohort 的实际共享技力总成本，并计算最早可整体释放的帧。例如两个首发战技各消耗 `100`，目标至少是 `200`。

这个模式仍需同时检查个人能量、冷却、连携有效窗等其它门控；如果所有门控没有公共可行帧，等待列应明确报告“后一组当前无可行起始时间”。

### 18.5 强制等待列就是分组封条

有了整列等待后，不再需要额外的“封组按钮”或隐藏分组状态：

- 插入等待列即封闭前一大组；
- 等待列右侧自然开启后一大组；
- 删除等待列意味着尝试合并前后组，必须重新验证所有尾链、资源与同时释放关系；
- 移动等待列意味着移动分界，受影响的整个后缀一起重新分组；
- 已封组的前一组内部仍可编辑，但不能把技能直接拖过等待列与后一组暗中连接；
- 需要跨组移动时，应以“移动整个动作后缀 / 重新分组”的显式操作完成。

### 18.6 占格与显示

- 无论等待真实持续 `0s、0.5s、3s` 还是更长，它始终只占一列；
- 该列的时间斜率由等待真实持续时间决定；
- `0s` 时是不可逆映射的纯视觉列；
- 正时长时，该列内部所有资源、状态和延迟事件按共享时间线性投影；
- 四个空白格应有统一选中轮廓，表明它们属于同一个列对象；
- 列头显示模式，例如“封组”“固定 2.0s”“技力至 200”“等待后组可释放”；
- 技力自然恢复可以显示在该列下方的共享技力条上。

### 18.7 它对并行尾链算法的简化

每个大组内部继续使用多条并行尾链与水位扫描；强制等待列只出现在两个大组之间：

```text
Group 1（内部并行尾链）
  -> WaitColumn（整列封组与等待）
  -> Group 2（新的统一左起点）
```

这样可以明确区分：

- 组内：技能或普通等待只能向角色尾链紧贴追加；
- 组间：只能通过整列等待跨越；
- 普通等待只顺延同一角色的后继；其它行仅共享由真实事件形成的列边界，不共享这条依赖边。

## 19. 第一版可执行算法模型

已建立一个与现有画布解耦的纯领域模型：

```text
demo/lts-ui/src/core/domain/sharedVariableRateTimeline.ts
```

当前模型已经把以下约束变成可执行规则：

1. 同一大组内，每条角色轨道按真实 `blocking duration` 首尾紧接；
2. 各轨道首发动作共用大组起始帧，大组结束取最长轨道尾帧；
3. 第二个及以后的大组必须显式拥有一列强制等待；
4. `seal-only` 等待推进 `0` 帧但仍占一整列；
5. 固定时长等待直接推进真实帧；
6. `atb-target / next-group-ready` 必须由真实运行时适配器求解，缺少适配器时直接报告未解析，禁止猜测恢复速度；
7. 所有同一真实开始帧的动作组成一个 cohort，共享技力成本先合计，再交给状态机适配器整体校验；
8. 没有状态机校验器时，结果只能是 `unverified`，不会被当作可执行；任一 cohort 无效时整条模型的 `isExecutable` 为 `false`；
9. 真实帧到 x 的投影按列线性计算；零时长等待列通过 `before / center / after` affinity 明确处理一帧多 x；
10. 技能主格、跨列范围和真实光标位置全部是派生结果，不参与反推真实技能时长。
11. 普通等待保存为组内 `laneWait`：它可以是占一格但推进 `0` 帧的占位，也可以有固定正时长；它只参与所在角色的释放依赖，不出现在整列 `waits` 中，也不增加大组数量。

第一版明确采用 `strong-event-boundaries`，也就是第 5 节所述“强事件边界模式”。这是为了先得到可解释、可验证且无循环因果的基准算法，并不表示第 5 节的交互取舍已经冻结。若最终选择紧凑投影，应增加第二种确定性列策略并用相同真实动作结果做投影，不能改写排轴求出的帧。

配套契约测试位于：

```text

```

测试覆盖终结技 `1.0s~3.1s` 后紧邻技能从 `3.1s` 起手、并行长短技能逐列变速、长技能跨多列、零时长封组列、固定与动态等待、同帧 `100 + 100 = 200` cohort 校验，以及未知规则不得伪装为合法。

## 20. 第一版运行时与画布接入（2026-08-26）

纯领域模型现已接入本地 AKE 预演、React 画布和正式小队结算入口：

1. `nodeIndex` 只保留组内顺序和旧数据迁移用途，不再换算请求帧；
2. 旧画布每 14 个节点形成一个明确的大组，后续非空组自动迁移为带 `seal-only` 整列封条的释放组；

9. 结算抽屉不再显示“一个节点等于若干帧”，改为标识“共享变速时间轴 · 强事件边界”；

## 21. 技能结算、可取消后摇与普攻连段（2026-08-26）

### 21.1 一个动作必须拆成四种时间

技能的原始动画总长不能再直接等同于时间轴阻塞时长。统一动作契约现在明确区分：

1. `commit offset`：伤害、投射物发射、资源或状态真正提交的帧；
2. `effect offset / effect end`：已经提交的效果实际落地或最后结算的帧；
3. `blocking end`：本角色允许开始后继动作的帧；
4. `natural end`：完全不取消时，原始动画身体自然结束的帧。

后继技能吸附和整列封组使用同一个截尾求解器：只有档案已经验证存在后继窗、可打断点、优先级中断或独占段结束，而且所有必需提交都已发生时，`blocking end` 才允许早于 `natural end`。未知提交语义一律保持 `unverified`，不能为了缩短按钮而猜测。

默认防抖为：

```text
debounceFrames = round(tickRate * 0.2s)
```

AKE 的 `30 Hz` 时钟下为 `6` 帧。若最后一个必需提交在 `H`，普通截尾不得早于 `H + 6`；真实后继窗口更晚时，以窗口起点为准。

### 21.2 截动画不等于删除已经提交的效果

- 直接伤害尚未发生时随动作取消而剪掉；
- 投射物尚未发射时随动作取消而剪掉；
- 投射物已经发射后，即使施法动画被截断，稍后的命中仍保留在 `effect tail`；
- 独立运行的延迟伤害、持续结算和 Buff 移除同理，不得因为角色恢复自由就凭空消失；
- 视觉按钮只画 `blocking interval`，伤害点仍按共享真实帧投影，允许落在按钮右侧。

运行时现在也接收规划器给出的动作结束帧。这样即使某条角色尾链后面没有同角色后继，整列封组仍会真正关闭可取消后摇、剪掉尚未提交的事件，并把命令标为 `interrupted`；不再只是在画布上把按钮画短。

### 21.3 普攻截段与连段游标

一个 A 按钮仍默认表示完整普攻连段，但当任何动作紧贴吸附到它后面时，不能擅自猜测打几段：

1. 画布弹出完整普攻轨道和逐段 hit 标记；
2. 用户选择执行 `1..N` 段；
3. 求解器只保留所选段的提交事件，在最后一段提交后加防抖；
4. 确认后，普攻和后继动作成为持久化原子 bundle；
5. bundle 不允许单独移动、改技能、复制或删除前半段；
6. 若要修改，右键删除后继动作，系统自动清除段数并恢复完整普攻，再重新吸附。

普攻动画是否被中断和普攻连段是否重置是两个独立状态：

- 战技、连携技、闪避、极限闪避：中断当前动画，但保留未完成段游标；
- 下一次 A 从未完成的阶段继续，只渲染本轮尚未完成的阶段；
- 终结技、显式“打断普攻”模块、跨过整列封组：把游标重置到第 1 段；
- 极限闪避恢复共享技力必须由真实触发状态机确认，拖入模块本身不能直接发放资源。

### 21.4 两个长时长异常的实证结论

佩丽卡普通战技的隔离时序档案为：

```text
raw duration = 155 frames
body end = frame 154
hit = frame 13
same-skill allow-next = frame 28..54
exclusive = 30 frames
```

因此约 `5.13s` 是原始动画身体，不是连续战技必须占用的阻塞时间。第一次命中后，第二个同战技应在 `frame 28 = 0.933s` 起手，而不是等到 `frame 154`。这属于旧规划器把 `bodyEndOffset` 当作唯一时长造成的代码错误，现已由关系截尾修正。

庄方易基础普通战技的隔离档案为：

```text
raw duration = 290 frames
projected body end = frame 190 = 6.33s
state/resource commit = frame 6
allow-next windows = frame 45..116, 120..147
direct hits observed by root probe = 0
```

它的 `6.33s` 同样不能作为连续输入的硬阻塞：已验证的后继可从 `frame 45` 开始。但“没有伤害”是另一处尚未闭合的运行时缺口。根技能负责施加御剑状态并 `SpawnAbilityEntity`；伤害位于生成剑体后触发的 Buff 链（例如 `buff_chr_0030_zhuangfy_sword_triggerd.json`），不是根技能直接 hit。当前隔离编译仍报告 `AKE_ABILITY_ENTITY_SKILL_MISSING`，并没有完整物化 owner 生成的 AbilityEntity、假目标、剑体选择器及其 Buff 状态机。因此当前只能正确压缩阻塞时长，不能伪造庄方易的伤害；后续必须补齐 AbilityEntity 执行链并用 Calc/AKE 对照验证。

## 22. 释放锚点 DAG 与第五站位（2026-08-26）

### 22.1 结构不是链表，也不是普通树

技能的真实起手关系采用有向无环图（DAG）：

- 每个动作至多拥有一个入边，明确回答“我为什么从这一帧开始”；
- 一个组起点、动作起点、动作尾部或伤害点可以同时被多个后继引用，因此允许分叉；
- 所有边只能向前解析，禁止自引用、悬空来源和环；
- 同一锚点的跨角色后继天然共享同一真实帧，画布格子不参与决定帧；
- 普通旧存档没有显式锚点时，才按同组同角色的节点顺序补出隐式前驱，保证迁移结果稳定。

当前允许拖放的有限锚点为：

1. `group-start`：顶格/大组左边界对齐；
2. `action-start`：与另一个动作同时起手；
3. `action-end`：紧跟另一个动作的可释放尾部；
4. `damage-hit`：某个已解析伤害节点之后，再加默认 `0.2s` 防抖。

拖拽期间只高亮这组可以解释的候选。落在普通空格、未知动画位置或超出磁吸半径时直接拒绝；`nodeIndex` 只保存显示顺序和旧数据兼容信息。锚点会同时进入运行时按钮、`timelineData`、`skillButtonTable` 与 Work Node checkout，载入后重新从关系图求解真实帧。

### 22.2 删除与移动规则

有后继依赖的动作不是分支末端，不能直接移动或删除。必须从各分支屁股开始向前拆；普攻截段 bundle 仍执行更严格的“删除尾部后继才恢复前驱”规则。

该约束同时存在于：

- 画布拖拽与右键删除；
- Work Node 指令入口；
- 时间轴领域服务；
- payload 镜像与 DAG 完整性校验。

因此不能通过另一个写入入口制造悬空锚点、跨组引用或循环依赖。

### 22.3 第五站位

右侧第五站位现提供四个全局可拖拽入口：

- 强制等待：只接受完整大组尾部或新组起点；占一整列，支持 `0s` 封组或固定时长，明确切断前后两组；
- 普通等待：接入某一角色的组内尾链；默认是占一格但推进 `0s` 的占位，可双击改成固定秒数，只顺延该角色的后继；
- 闪避：可吸附组起点、动作起点、动作尾部与伤害点；
- 极限闪避：锚点规则同闪避，但技力返还必须由真实极限闪避状态机确认。

两个等待入口拥有不同领域对象：普通等待是 `lane-wait + laneWaitConfig`，强制等待是 `forced-wait + forcedWaitConfig`。它们都不会伪装成 Dot 伤害进入伤害报表，也都使用带真实起止秒数和左右光标的区间 UI，不再复用“圆形图标 + 方形技能底座”。只有强制等待绘制贯穿四名干员的整列背景并改变大组；普通等待只绘制所在角色行的区间，固定秒数按 tick rate 量化为真实帧，零时长占位则只占视觉格而不推进状态机。

仍未闭合的是闪避时长、无敌窗、极限闪避判定/返还，以及“等待到目标技力 / 等待到下一组可释放”的动态求解器。只要排轴含闪避类未闭合模块，规划结果必须标成 `unverified` 且不可正式结算，不能用猜测数值冒充已实现机制。
