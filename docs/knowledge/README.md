## 如何维护

对话出现特殊叫法、用户专门解释的概念，或经过较大成本才厘清的源码/数据结论时，及时沉淀。先查已有条目；稳定术语定义归入 CONTEXT.md，长解释与角色结论按主题单独成文，再补本索引的关键词和触发场景。用户已明确解释的知识可以直接记录；提炼新的实验方针仍按 [从用户指导中学习](../guides/agent-development.md#从用户指导中学习) 先提出建议。

每个条目前几行写清：依据的代码提交及提交日期、分析/核验日期、数据版本或用户解释来源、本次内容提交的版本索引。正文至少留下结论、证据路径、适用条件和未决项。基于工作树的发现标明未提交，附可追溯 Run 或来源指纹；不能把旧 HEAD 写成修复所在提交。

阅读条目时先核对基线和相关变更。数据版本或相关实现变化后，保留旧证据，标记待复核；重新验证后更新条目及版本索引。术语更正同步到实验指南，避免错误定义在其他入口继续生效。

完成文档或代码的一项连贯工作后，鼓励及时本地提交。条目正文提交后，用 `git log -1 --format='%H %cI' -- <条目路径>` 登记实际哈希和日期，再提交索引更新。正文有新改动时索引标为待更新，不能沿用旧哈希冒充本次版本。提交与推送/部署分别处理，具体范围见 [开发习惯](../../AGENTS.md)。

知识库负责让结论可找回，不取代原始数据、运行证据、当前架构或待批准 Spec。历史审计保存发现过程，本库保存可复用解释与它们的阅读路由。
