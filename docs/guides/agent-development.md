# Agent 实验、分工与自迭代

本指南定义开发过程；它不增加游戏规则，也不表示探索记录中的候选任务已获实施授权。根 [AGENTS.md](../../AGENTS.md) 负责触发阅读，[探索记录](../maintenance/engine-exploration.md) 负责保留结果、未覆盖组合与提案状态。

## 实验

### 先写可证伪的问题

1. 查探索记录及对应 RIA Run，选择尚未覆盖、证据矛盾或与此次改动相关的一条分支；写出预期和能推翻它的观察。例如“追加后继输入会不会改变其影响发生前的寒冷层数”。
2. 固定来源版本、代码版本及 dirty 摘要、队员、主控、敌人、装备、技能等级/潜能、随机条件、初始资源/状态、输入与结算终点。以实际有效 loadout 为准，配置留空也要展开引擎默认值。
3. 先跑基线，再改变一个因素，比较第一处分歧的输入→准入→施法→事件→状态→命中→报表链。完成条件是定位分歧所属层，或明确记录该范围内未观察到差异。
4. 减少无关动作，保留最小复现。机制修复后再加入装备和队友交互；相关用户路径用真实 Chrome 操作及 RIA 复核，包含保存/恢复时就实际走完存档链。

### 装备与热启动

常规开发实验采用 [默认配装习惯](../knowledge/experiments/default-loadout.md)。下表的最小配装只用于有明确因果问题的隔离实验，实战伤害比较通常装齐武器与四槽装备。

| 目的 | 条件选择 | 结论范围 |
| --- | --- | --- |
| 隔离机制 | 固定最小配装，记录实际默认武器；通过已支持配置禁用可选触发，不能隔离时明确列出 | 该固定配置下的机制因果 |
| 验证装备交互 | 在基线上一次加入一个武器、套装或触发条件，最后核对组合 | 新增来源如何改变状态、倍率和归因 |
| 优化实战排轴 | 固定完整有效配装、队伍和敌人，所有候选共用 | 该配装与搜索范围内的最佳已验证方案 |

本项目“热启动”的含义以 [项目术语](../../CONTEXT.md) 为准，场景设置见 [知识库条目](../knowledge/terms/hot-start.md)。实验分别记录：

- **战斗初始条件**：热启动按用户指定的全员满终结技能量建立，不额外要求充能预备轴。共享技力、Buff、寒冷、冷却与主控单独明确；若另外研究预备过程，则记录其可达性及耗时、伤害、资源计费。人为注入其他状态的机制实验单独标注。
- **服务预热**：记录进程是否已加载/编译数据，以及首次启动或预热后运行。服务预热不得继承上一候选的可变战斗状态；固定输入在两种运行条件下结果应一致。

### 有限战技排轴搜索

用户未另定口径时，以**全队最多三次主动战技输入**作为探索起点；普通战技替代为瞬时施法也占输入预算，派生/追击单独统计。三次限制只约束主动战技，不代表允许无限普攻、连携、终结技或预备动作。

开始搜索前公开场景卡：战技计数、其他技能/等待/换人上限、固定战斗终点或完整动作集合、预备阶段计费、资源可达性、配装与主要指标。纯等待积累或拖长结算不能无界提高目标。默认固定条件下比较期望总伤害；DPS 同时列出且分母固定，不在结果出来后切换指标。

搜索按以下层次展开：

1. 在固定技能多重集合内枚举主动战技顺序，先用零到三次前缀检查准入与状态。探索记录保存候选 ID、输入摘要/哈希、可重放路径和结果，避免重复猜测。
2. 为合法候选增加有限释放位置：动作起止、实际命中、连携触发/到期附近；检查边界前一帧、同帧与后一帧。同帧顺序、角色局部帧与全局帧分别记录。
3. 再探索有目的的换人、连携、终结技和配装触发组合。组合过大时用成对覆盖或有界搜索，并报告覆盖的分支、候选数、剪枝理由和遗漏。
4. 对最佳及机制不同的代表方案，用全新战斗实例重放；核对资源、前置状态、逐次命中、伤害归因、重复运行与历史前缀。最终通过真实 provider/API/Chrome 确认可操作性。

只有在声明的有限空间全部搜索、前置可达且相关机制已验证时，才称该空间的最高伤害；其余写“已搜索范围内最佳”。不支持的动作或部分结算候选保留为诊断结果，不能进入已验证最优排名。本段是可执行方法，不声称已有自动优化器。

### 交叉验证与停止条件

- 追加动作：只比较其最早因果影响之前的历史；若追加改变了实际释放依赖或战斗终点，先按共同观测区间核对。未来追加不会改写过去，但新的同帧事件可能合法改变该帧之后的结果。
- 前缀独立性：相同初始状态与输入多次运行、候选执行顺序交换、服务预热前后，语义结果应一致；如顺序本来具有含义，先明确该合同。
- 身份与寿命：分别改变主控、施法者、来源实体和目标；覆盖自然结束、提前结束与同根多次派生。
- 停止：已解释原问题，最小复现和受影响的跨角色/UI 路径通过，剩余边界被记录。探索任务用事先声明的有限空间及剩余问题收口；需要扩展范围时说明预期信息收益。

## 子代理分工

先判断任务是否独立、输入是否固定、输出是否可核验，以及主代理同时能推进什么。小型连续编辑或需要同一 Chrome 活动状态的任务由主代理完成；仅整理开发约定这类没有独立并行工作的任务，本地完成即可。

| 工作 | 选择 | 交付要求 |
| --- | --- | --- |
| 定位字段、核对少量原始数据、运行已定义的候选排列、整理证据索引 | 可交给 `gpt-5.6-luna` / `max`，仅在当前工具支持时；能力不可用则用可用模型并说明 | 固定输入、明确范围、原始结果/来源位置、异常与未知；主代理复核关键样本 |
| 开放式机制诊断、跨模块因果、缓存失效与可恢复状态设计 | 主代理或具备相应能力的代理 | 第一处分歧、反例、通用修复边界；主代理负责合并判断 |
| 不同角色或不同机制面的独立审计 | 子代理分别负责限定范围 | 各自证据与写入文件边界；共同核心修改先协调所有者 |

Luna 是成本与任务匹配的选择，不是正确性的保证；`max` 也不能替代可核验输入与复核。代理暴露歧义、需要扩展范围或发生重复错误时，主代理接手或升级分析，不让低成本任务滚成无界探索。

每次分派包含：问题、固定输入/源码范围、可写路径、停止条件、预期产物，以及独占 UI/共享文件约束。代理数量服从实际并行收益与可用槽位，不机械按角色数拉满。主代理负责用户 Chrome；其他代理优先独立运行时/API 夹具。

记录此次为何委派或本地完成、选用模型、实际耗时/已知用量、有效发现和返工情况；拿不到用量时标为未知。下次据此调整分工，不仅按模型名称推断能力。

## 优化提案

开发过程中随时留意值得改进的体验、机制、结构与工作方式，发现有价值的方向就先与用户交流。几句话讲清观察、想法与收益即可，证据不足的部分标为假设。主动性贯穿开发，不必等到任务结束复盘或用户再次提出问题。

当想法值得进一步实施时，再按影响大小选择下面的步骤。重复编译/重算、增量编辑全量重放、巨型对象多份复制、日志进入交互关键路径或同类修复反复出现，都是值得追查的信号；这些步骤服务于判断，不是提出想法前必须填完的流程。

1. 记录真实触发操作与量级：输入/事件数、响应字节、分阶段耗时和内存；分清服务启动、战斗执行、投影、归档、传输和渲染。测量工具自身成本也应说明。
2. 找到数据所有者和重复发生的位置，检查已有缓存或复用机制，给出源码证据。观察快照、显示投影与可恢复执行状态分别命名。
3. 形成具体提案：用户收益、最小实施边界、受影响文件/合同、失效条件、验证办法、回退方式、未知成本。数量收益只引用实测或标明预测。
4. 当前授权范围内的探索与必要修复继续做；超出授权、需要用户选择方向或接受额外成本时，再提出可评审的实施申请。仅改变内部实现方式不自动产生新审批；未回复的实施申请保持待确认。
5. 获批后落实、测量前后变化，更新状态和权威文档；仅提案时保持实现事实原样。

增量排轴的关键审查：确认最早受影响的事件边界；输入、配装、敌人、初始状态、主控、版本和随机条件决定复用资格。断点必须保存全部可继续执行的状态、事件顺序和延迟动作；只缓存历史 Hit 或将展示 snapshot 直接反序列化，不能证明可续跑。始终保留从头计算作为对照与失败回退，内存预算、缓存淘汰和取消/过期结果也属于设计。

## 从用户指导中学习

用户调整问题范围、指定实验条件、要求新的对照或指出推理遗漏时，同时留意其解题方法。例如，“限定三次战技再比较排列”体现了先收敛搜索空间、再寻找反例和更优方案的思路。分析这种方法解决了什么盲点、为何有效、换一个角色或问题是否仍适用；区分用户已明确要求的习惯、待验证的具体判断与 Agent 自己提炼的方法。

发现特别值得复用的方法，及时向用户说明“我从这次指导中学到了什么、以后什么情况下可用”，并建议具体的路由文字和文档落点。表达可以简短，不必先写完整提案；用户认可后合并进已有方法及 AGENTS.md 指针。仅适用于当前案例的条件留在实验记录，避免把一次指导扩大成所有任务的固定要求。

## 自迭代

每次重要机制调查、性能修复或重复工作结束，做一次短复盘：原假设错在哪里、哪种实验最有效、哪些步骤浪费、有没有值得主动告诉用户的改进方向。能复用才写规则，只适用于该角色/输入的事实留在记录；记录用于帮助下一次思考，不以增加规范数量衡量自迭代。

| 内容 | 唯一落点 |
| --- | --- |
| 已获用户认可的稳定开发习惯与触发路由 | 根 AGENTS.md；细节放本指南 |
| 已跑排列、否定结果、未覆盖分支、代理效果 | 探索记录，引用 RIA 或带日期审计；大结果放 artifacts |
| 待批准的优化或习惯变更 | 探索记录中的提案，写明证据与待确认状态 |
| 已接受的新产品行为或跨模块合同 | Spec / ADR；遵守现有文档格式与职责 |
| 当前实现和证明范围 | 架构 / 生成证据 / 可执行回归；分别维护 |
| 对话术语、昂贵源码/解包分析与可复用角色结论 | [知识库](../knowledge/README.md)，记录来源版本并补路由；术语定义唯一存于 CONTEXT.md |

本轮用户已经授权建立这些习惯及路由，日后修正断链、去重、补充已验证的操作说明可直接完成。新增会改变需求、审批、模型开销或维护负担的规则，先展示具体文本和理由，再申请写入。

修改时合并已有同义规则、删去过时指针、保留被替代记录的去向；核对相对链接和冲突规则。纯文档更新检查链接/结构、事实与差异即可，生成证据输入变化才检查/重建相应证据，业务行为变化才执行相应行为验证。

鼓励完成一项连贯的代码或文档改动后及时本地提交，避免知识与实现长期只存在工作树中；检查暂存范围和既有改动，再报告提交号。知识正文提交后登记真实版本索引，不伪造未提交哈希，也不把旧 HEAD 当成新修复的证据。提交不自动授权推送或部署。
