# 排轴执行顺序与渲染分离 Spec

## Status

**Status:** Accepted for implementation（2026-09-12，用户授权先定规格与任务，再交给两个既有实现任务）

**Implementation:** Not implemented；本文件与 [tasks.md](tasks.md) 是本轮施工依据。

**Baseline:** `9ff9f94`（2026-09-12），业务基线为 `618921d`；此前阅读、批量、压缩及状态归属效果继续保留。

**Scope:** 桌面 AKE 排轴从已保存输入、预演、请求构造到小队引擎的时间与同帧操作先后。包含必要的旧输入兼容、存档往返、执行身份和 RIA 记录。

**运行约束：** 用户 2026-09-12 明确要求期间不要主动打开或重启浏览器，现有 Node 服务供其他地方使用。本轮所有实现与检查在独立工作树完成；不启动浏览器（包括 headless）、不导航/刷新现有页面、不重启/终止现有 Node/Vite/RIA、不向活动会话发重算或编辑命令、不占用现有端口。主任务也遵守。代码完成先交付独立提交，主库接入与浏览器验收另行协调，不能为本轮检查影响正在使用的服务。

## Problem Statement

像素用于渲染没有问题，但当前显示几何反向进入了执行决策：

1. `akeProvider.runAkeTeamCalculation` 把技能 `startX`、切人 `endX` 发送为 `timelineOrder`。
2. 小队 runner 在同帧技能/切人及同一来源唤醒的多个后继中使用该数值排序。
3. `operatorControlTimeline.controlledOperatorAt` 使用 `endX <= x` 判断同帧切人是否已经生效；预演的瞬时施法替代、普攻与闪避主控校验也调用它。
4. 执行摘要仍部分引用旧节点表示；不能只换请求字段名而让预演或缓存继续受几何驱动。

这些路径由源码确认，不表示已经在当前浏览器复现了缩放引发的伤害变化。此次修复的是职责混用；完整审查同时覆盖预演、输入与结算，不能仅删除两个赋值后宣称完成。

## Solution

建立单向合同：**持久化操作意图 → 逻辑时间/顺序 → 引擎结算；逻辑计划及结算事实 → 渲染投影。**

时间仍由帧和接续依赖表达。相同帧不能消除“切人先还是攻击先”之类差异，因此另用无单位的稳定操作序号，只在已到达、同帧且同一调度相位的独立操作间排序。序号不是秒、帧、像素或技能优先级。

### 共享 Interface：两个任务必须照此接线

前端持久化在 `TimelineData` 增加可选字段；字段缺失表示旧存档，不是自动把所有序号置为零：

```ts
type TimelineOperationSequence = {
  schemaVersion: 1;
  operationIds: string[];
};
// TimelineData.operationSequence?: TimelineOperationSequence
```

`operationIds` 是本工作副本全部操作的稳定身份序列，技能、切人、普通等待、封组等待、闪避等都参与；每个实际存在的操作 ID 恰好出现一次。它负责明确原输入先后，不替代分组、角色队列、释放依赖或主控。当前持久化 `nodeIndex/staffIndex` 在队列/分组适配中的既有语义暂保留，不能把其数值当帧、像素序或新序号；本轮不整体替换 DEF 文档结构。

提交给小队接口的 v1 格式：

```ts
{
  operationOrderVersion: 1,
  commands: [{ commandId, frame, operationOrder, releaseDependency, /* 原字段 */ }],
  operatorSwitches: [{ switchId, frame, operationOrder, releaseDependency, /* 原字段 */ }],
  // 队伍、敌人、资源、主控、终点等原输入保持原合同
}
```

- `operationOrder` 为该 ID 在已校验 `operationIds` 中的索引，非负安全整数。只传实际可执行技能/切人，所以允许序号有空档；它们共用同一命名空间、序号不得重复。
- 依赖优先：来源真实起手、结束或命中发生后，后继才能被调度；零延迟仍在来源事件之后，不修改事件优先级来让后继抢在原因前执行。
- 时间优先：不同时刻按帧，不按序号。多个来源逐次产生的事件保留真实因果顺序；序号不把尚未满足的依赖拉到前面。
- v1 请求不包含 `timelineOrder`。API 与直接 runner 都校验：不支持的版本、缺失序号、负数/小数/非有限/不安全整数、重复序号、重复身份及 v1/v0 混用明确失败，不静默降级。
- 无 `operationOrderVersion` 且无新字段的历史输入仍按原 `timelineOrder` 和旧 tie-break 执行。v0 仅是旧 API / RIA 重放兼容，不供新前端继续生成。
- 请求序号必须进入有效输入摘要及可查的运行记录；快照、API、预演和 runner 不能各算一套序号。

这是一条共享 Interface，不要求引擎消费前端 `TimelineData`、React 对象或完整节点树。前端适配为数值帧、关系和序号后提交。

## User Stories

1. 我改变压缩、分页或阅读模式，只改变显示；技能先后、主控、伤害与附着不变。
2. 我在同一帧安排切人和攻击，保存的先后明确；重新读取不能把它们交换。
3. 多个技能跟随同一个命中，以明确的顺序接入，不由按钮放在哪一行或渲染回调顺序决定。
4. 旧轴仍能读取，原操作意图和已知结果可以对照；迁移不能悄悄保存或重建我的历史节点。
5. 调试时我能看到请求的逻辑序号，并区分真实时间、同帧先后和纯显示坐标。

## Requirements

### Requirement ORDER-01: 在几何之前形成逻辑操作序列

系统 SHALL 由一处纯逻辑 Module 负责操作序列的读取、校验和编辑维护。该 Module 不访问 DOM、Canvas、CSS、视口或 frame→x 投影。

#### Scenario: 新建与追加

- GIVEN 新建工作副本的序列为空
- WHEN 用户提交一个新操作
- THEN 通过唯一业务写入口把新 ID 追加到逻辑序列；在同帧无其他因果关系时，它排在已存在操作后
- AND 显式接续仍通过依赖决定实际时间，不能用追加序号替代来源关系
- AND 取消草稿不改变序列，不产生存档写入或额外结算

#### Scenario: 编辑、删除、撤销和重读

- WHEN 编辑已有操作的接续/配装或显示位置
- THEN 其身份与已有序列中各操作的相对先后保持不变
- WHEN 合法队尾批量删除及撤销
- THEN 删除只移除对应 ID，撤销恢复原快照序列；普攻拆段联动清理遵循原单项删除语义
- AND 保存、SQLite 节点 checkout、v2 文件往返、导入、打开、新建/切换文档均保留或正确初始化序列
- AND 硬重建 payload 的兼容路径不得丢字段；读到已声明 v1 的损坏序列明确报错，不能当作旧存档重排

合法业务编辑中增删 ID，由已知的编辑操作维护；通用读取校验不能为了“修复”未知数据而自动追加/删除 ID。

### Requirement ORDER-02: 旧存档有确定的兼容解释

系统 SHALL 将无序列的旧工作副本转为可核对的逻辑序列，保留旧版同帧先后。

**兼容权威（2026-09-12 补充）：** 固定基线的同一输入经旧 provider → demo 规范化 → v0 runner 后的实际调度，是迁移必须保留的合同。旧预演另有 `characterId` 排序，与该合同不一致时，记录第一处分歧，让新预演对齐实际执行；不要求同时保留两套互相冲突的旧顺序。没有已存运行记录时，用固定基线离线纯调用取得对照，不猜测用户意图。

旧相等键也属于兼容合同：初始调度按帧、旧 `timelineOrder`，相等时切人先于技能，同类保持其规范化后的稳定顺序；同来源依赖候选以旧顺序键及稳定插入序排序。迁移须同时核对两处 fallback，包含缺省键、技能规范化和切人数组顺序。若单个静态序列无法表达两处旧行为，提交最小反例及第一处分歧给主任务裁决，不能修改 v0 结果迁就迁移。

#### Scenario: 读取旧轴

- WHEN 无 `operationSequence` 的旧存档被读取
- THEN 在内存创建迁移副本，保留原对象、节点和时间戳；用户正常编辑/保存时才持久化新字段
- AND 独立的旧格式 Adapter 重现旧基线的排序，包括零时长控制两侧、同帧技能/切人相等键的旧规则
- AND 允许该兼容 Adapter 读取旧存档原有节点结构，并以固定旧排序语义作一次转换；不得读取当前 DOM/CSS/可见压缩参数，不得把新渲染器的坐标作为迁移依据
- AND 若确需重现旧版投影来取得原相对排序，仅限命名清楚的 legacy Adapter，固定基线和参数；立即转换为无单位序号，禁止进入 v1 的预演/执行路径，禁止通过“每次重绘迁移”保留耦合
- AND 无法证明旧相对顺序时暴露迁移诊断，交主任务裁决，不按角色字母顺序或新画面猜测

迁移前后的既有九动作、洛茜/卡缪输入及含同帧切人的小输入必须对照。历史 sealed Run 与原 `fixtures/ria/*.json` 不改写；v1 对照另建小夹具或程序化副本并标来源。

### Requirement ORDER-03: 预演与准入不再用像素判断主控

系统 SHALL 在预演、瞬时替代、普攻/闪避/切人校验和拖入候选中使用同一逻辑位置。

#### Scenario: 同帧切人的前后

- GIVEN 初始主控 A，F50 的切人序号为 7
- WHEN 查询 F50、序号 6 的操作
- THEN 主控仍为 A
- WHEN 查询 F50、序号 8 的操作
- THEN 使用切人目标 B；查询切人自身的 before/after 时明确区分相位
- AND 不加 0.001 帧或 1 帧来伪造先后，不用 startX/endX 比较

同帧有多个切人时按逻辑顺序逐个应用；重复 ID/序号是数据错误，两个不同合法顺序的切人不能仅因同帧被判成同一个操作。

#### Scenario: 后改依赖不能被创建序号倒置

- GIVEN 早先创建的动作 C（序号 1）后来被编辑为跟随同帧切人 X（序号 7）结束、偏移为零
- WHEN 预演或准入查询 C 的主控
- THEN X 已生效；持久化序号不变，来源依赖决定实际先后
- GIVEN 同帧独立切人 X（序号 5）、独立技能 S（序号 7），C（序号 1）跟随 S 起手
- THEN 实际为 X → S → C，C 也看见非祖先 X 的切人效果；仅将依赖祖先加入查询不够
- AND 两个来源分别唤醒后继时保留各自到达批次，不能将全部后继重新按创建序号全局排序

`{frame, operationOrder, phase}` 只足以查询没有上述依赖的独立同帧操作。统一控制计划须使用逻辑计划/预演解析出的执行位置，区分持久化意图序和派生的实际同帧位置；后者可以用操作身份及 `dispatchOrdinal` 或等价事件位置表示，不持久化、不发给引擎代替原序号。该位置必须遵循 ORDER-04 的来源事件、相位和 ready 批次合同，供预演、主控校验与草稿共用。复用现有求时/预演，不能用各调用点的祖先补丁、拓扑排序后直接按序号重排，或另抄一套伤害/资源引擎来解决。

#### Scenario: 鼠标选位置

- WHEN 用户拖入新操作
- THEN 鼠标坐标只用于命中候选；候选先转换为来源 ID、接续关系、帧及草稿逻辑序，再校验主控和准入
- AND 已入队按钮仍不可拖动，原阅读/批量/尾删规则不改变
- AND 操作来源不再有效时明确取消或拒绝，不回退到鼠标当前 x 推导执行位置

保留独立的显示查询函数也可以，但其结果不能用于业务准入；所有原 `controlledOperatorAt` 调用点须审计，不以函数注释里的“pixel-independent”代替实际检查。

### Requirement ORDER-04: 引擎只使用显式时间、因果与序号

系统 SHALL 贯通请求规范化、直接 runner、工作线程、RIA 与实际调度，不在中间排序时丢弃新序号。

#### Scenario: 相同来源唤醒多个后继

- GIVEN 两个后继都跟随同一次实际命中且偏移为零，operationOrder 分别为 12 和 9
- WHEN 来源命中事务完成
- THEN 在同一可调度批次里先处理 9，再处理 12；即使 commands 数组顺序相反也一致
- AND 状态/命中事务原有优先级不改变，来源失败/未命中时不制造后继

#### Scenario: 请求数组重排与旧输入

- GIVEN v1 的技能和切人身份、时间、序号及依赖相同
- WHEN 仅重排 commands / operatorSwitches 数组
- THEN 结算及调度顺序不变；规范化也不能用成员名改变 v1 顺序
- GIVEN 旧 v0 fixture 未包含新版本字段
- THEN 仍按原合同重放，包含默认切人顺序和显式旧 timelineOrder；不得在此分支偷偷套用 v1 规则

### Requirement ORDER-05: 执行身份只描述业务输入

系统 SHALL 从规范化逻辑输入构造有效计算摘要，显式标记合同升级。

- WHEN 时间、接续关系、逻辑顺序、主控、队伍/有效配装、敌人、数据版本或结算终点改变
- THEN 摘要失效，旧报告不能作为新输入结果
- WHEN 只改变阅读模式、像素位置、压缩比例、页宽、纯派生行号、更新时间或报告批注
- THEN 摘要不变，不因为显示重新触发模拟
- AND 旧 `nodeIndex/staffIndex` 仍承担分组/队列语义时，不可一律删除后漏算真实输入变化；应纳入解析后的逻辑关系/分组表示
- AND RIA 记录输入版本及每个操作序号，像素如用于观察只留在 UI section，不混进引擎输入

## Implementation Decisions

- 优先在现有共享时间轴的 schedule/preliminary 阶段提取帧、角色行、操作身份和逻辑序，不另起第二个时间求解器。`makeActivityColumns`、压缩、分页、materialize 的 x 仍属于渲染职责。
- 同帧控制采用“现有预演发来源事件 → 纯 ready/控制 dispatcher → 派生控制计划”。绝对输入预先入 ready，依赖只注册 pending；来源真实发生时按本批序号唤醒，以帧、原相位和 FIFO 入队次序消费。dispatcher 只管理操作到达、切人与 before/after 位置，不计算伤害、资源或技能时长；queued 重试也沿用这条到达顺序。自然结束、打断结束和真实命中的通知由预演对应事件处发出，不能仅凭 preliminary 的最终帧预先制造来源事实。缺少可确定的来源时保留诊断，不猜测合法主控。
- 窄的纯 Interface 负责 `validate / migrate / apply-edit` 序列操作，输入/输出普通数据。统一实现后供 provider、预演、存档与草稿校验使用；不散落多个 Array.sort 补丁。
- 新持久化字段在 `TimelineData`，无需 SQLite 表迁移或 v2 容器整体改版；既有白名单/显式构造需要保留字段。
- 前端拥有 v1 逻辑序列与新请求产生；根引擎拥有新旧请求合同校验、调度及历史重放。两个任务不跨文件所有权修改对方代码。
- 未解析等待/闪避等控制模块仍按现有边界显示；记录序列不等于新增这些模块的引擎能力。
- 不改变 AllowNext、命中锚点范围、连携准入、伤害公式、资源规则、持续 Buff 生命周期或战斗终点算法。

## Testing Decisions

仅做与此 Interface 相关的离线检查，不运行需要浏览器或会影响现有服务的脚本。既有 `run-ts-test.mjs` 使用 `middlewareMode: true / hmr: false / ws: false`，不 listen 的隔离 SSR 检查允许使用；不能启动第二个开发服务来替代它。

| ID | 验收行为 | 方法 |
| --- | --- | --- |
| AC-01 | 新前端请求不含像素排序、完整且唯一的 v1 序号进入接口 | 纯请求构造断言及源码数据流审查 |
| AC-02 | 压缩、页宽、阅读和坐标改变不改帧、序号、准入和摘要 | 同一逻辑计划的多种显示投影对照 |
| AC-03 | 同帧切人在攻击前/后导致符合规则的主控差异 | 前端纯主控查询 + 根 runner 同输入对照 |
| AC-04 | 同来源多个零偏移后继遵循序号，原因先于后继 | 真实 runner 事件序列 |
| AC-05 | v1 数组乱序后结算一致，v0 既有重放不变 | 版本化输入对照，不只比较总伤 |
| AC-06 | 旧序列迁移确定、幂等，不写原节点；新格式损坏明确失败 | 旧真实 payload/最小控制输入与纯迁移检查 |
| AC-07 | 保存/重读、v2 文件/节点往返、删除/撤销保留顺序 | 内存或隔离 SQLite/存储适配，不读写用户库 |
| AC-08 | 资源/关系/逻辑顺序变则摘要变，纯 UI 变则不变 | 有效输入身份检查 |
| AC-09 | 版本/序号异常在 API 与直接 runner 均失败 | 少量具体失败边界，版本兼容及空轴 |
| AC-10 | 九动作与洛茜/卡缪案例的前后操作、主控、命中、附着、资源一致 | 固定配装/终点，用旧输入和 v1 对照；差异逐事件解释 |
| AC-11 | 类型与依赖接线可构建，已有阅读/批量布局未被改写 | 两任务合并到隔离集成工作树后 typecheck、必要构建与差异审查 |
| AC-12 | 用户 Chrome 可用且原输入保持 | 本轮按用户约束延期；不能冒称已完成浏览器验证 |

如新合同使某个历史同帧行为变化，必须给出具体第一处分歧和迁移错误/旧合同缺陷判断，不通过更改期望伤害让测试变绿。保留有价值反例，避免新增只复述字段赋值的庞大测试套件。

旧预演与旧实际执行原本不一致时，AC-06 / AC-10 以 ORDER-02 的实际调度合同为对照；单独列出新预演修正，不能把预演差异误报成已保留的旧引擎结果发生变化。

## Out of Scope

本轮不实施 AllowNext 新接点、全局效果轨道、原因详情 UI、前缀缓存、伤害搜索、手机端、DEF 数据库重建或发布。仅给这些后续功能建立不依赖渲染的输入合同。主库合并、服务接入和浏览器验收不能影响其他任务正在使用的 Node 服务。
