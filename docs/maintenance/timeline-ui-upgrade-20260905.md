## 现有水位模型应该保留什么

源码中的水位求解首先处理各角色动作与控制关系，再以动作起止、等待、切人等强边界切列。等宽列可以包含不同帧数，多角色在同列共享同一时间斜率。其价值是让并行动作可读，并使短动作与长动作在共同进程中接续。

必须保留：真实帧权威、共享映射、稳定同帧顺序、阻塞时间与效果尾链分离、明确的等待/封组语义。原 DEF 的工作台与节点编辑可继续复用。DEF 固定几何不是 AKE 执行时序的来源；本方案也不另起一个独立伤害报表体系。

参考：[当前共享变速架构](../architecture/shared-variable-rate-timeline.md)、[原设计推演](../archive/initial-research-series/SHARED_VARIABLE_RATE_TIMELINE_DESIGN_NOTES.md)、[共享投影实现](../../demo/lts-ui/src/core/domain/sharedVariableRateTimeline.ts)。

## 必须先修的正确性问题

1. **接续关系被丢弃。** [akeProvider](../../demo/lts-ui/src/integrations/ake/akeProvider.ts) 的 `releaseDependencyFor` 只保留部分非终结技 damage-hit 依赖；action-end 等关系换算为预演帧。用户的“结束后”不能随着真实结束更新。
2. **像素参与同帧执行顺序。** 同一 provider 用 action.startX/switch.endX 生成 timelineOrder；[小队 runner](../../src/core/ake-squad-scenario-runner.mjs) 用它排序同帧输入。压缩、展开、换行之前，需要与显示无关的稳定顺序。
3. **派生命中按技能名启发式分组。** [CanvasArea](../../demo/lts-ui/src/components/CanvasBoard/components/CanvasArea.tsx) 通过角色、skillId和时间反认命令。成功汤汤样本的37个 water_projhit burst 跨三个rootCast，却得到同一fallback groupKey。应消费运行时已有的根施放身份，并保留独立触发身份。
4. **尾伤被夹到最右边。** 同一 Canvas 的 `visualPointForFrame` 把超出最后动作的帧夹到轴末。成功汤汤轴动作最后532结束，539/547两次尾伤因此落在同一横坐标。保护尾伤“不占操作格”不等于把它们压成同时发生。
5. **密集候选难以选择。** 当前吸附仍依赖最近像素与种类优先级。压缩后同一区域可能对应末击、精准窗、动作结束等不同含义，需可选择的语义候选。

上述问题应单独取证修复，不能借 UI 改造改变数值后宣称“体验改善”。当前按条目数超过12就抽样至8点的策略也不适合新模型：它没有考虑像素间距、根实例或关键事件，不能当作无损汇总。

## 推荐的操作与显示方式

### 操作骨架与效果带

角色主行保留技能、切人、等待、接续线；动作记录以紧凑条表示。每次施放的持续效果在其下方独立显示，延迟首伤、周期伤害、派生实体、反应尾伤继续占据自己的真实时间范围。

同一技能的 B①、B②、Q派生有不同实例归属。切主控不改变后台效果所属角色。选中效果时同时高亮其根施放与触发动作；跨角色触发不能把伤害搬到触发者一行。

需要组合操作时，从节点选择“接续动作”，指定操作者和接续依据。若缺主控切换，生成一条可见、可编辑的切人步骤。画布可折叠显示 `汤汤Q → 切汤汤 → 落地`；展开仍是独立命令。必须区分“指定落地动作开始”与尚未建模的起跳/飞行过程。

### 接续入口按含义组织

默认提供当前动作真实支持的少量入口：动作结束、指定命中、精准输入窗口、由事件生成的连携机会。最早可接续时刻可能随后继动作类别变化，不能由一个通用 endFrame代替。普通 DOT tick 默认只读；当某个tick确实产生了可操作窗口时，提供的是窗口入口，不是把所有伤害点开放为吸附点。

压缩区域有多个候选时，显示名称、来源和帧范围的小菜单。用户选中精准窗口后局部展开，可选窗口内位置并用键盘微调。保存稳定的来源动作ID与语义事件选择器；运行时 eventId只负责定位该次结算，不能直接冒充可跨重算保存的引用。

“按关系接续”和“固定帧输入”分开：前者等待所选事件满足，后者严格检查指定时刻。不得将当前被拒绝的固定落地默默延后。源动作失败、窗口失效或依赖循环时，在受影响节点显示具体原因。

### 三种视图共用一份结果

| 视图 | 使用场景 | 取舍 |
| --- | --- | --- |
| 紧凑总览（默认建议） | 观察队伍协作、组合顺序与长尾 | 分段非等比例，必须明示刻度和压缩区间 |
| 聚焦所选 | 编辑精准窗口、区分相邻帧、选择吸附事件 | 放大局部，其他角色同步改变同一段比例 |
| 等时核对 | 核对节奏、延迟和持续时长 | 时间直观，但长轴需要更多横向空间 |

不推荐各角色独立压缩：它使同一帧横向错位。不推荐把所有事件做等宽卡片：79次命中会挤占操作空间，持续时间也不直观。不推荐把每个DOT结束设为下一操作边界：会制造不存在的阻塞。

## 视觉压缩的具体规则

1. 从已解析结果取得全局时间范围，覆盖所有真实伤害；很长但不再产生伤害或操作机会的Buff寿命用延续标记表达，不无限拉长主轴。
2. 全队共同生成分段。关键边界包括控制变化、已选命中、窗口起止、状态获得/消费、跨技能触发；普通重复tick不逐个制造一列。
3. 正时长区间始终保留正显示宽度，段内线性映射。普通区间按持续时间与内容密度分配宽度；长且少决策的区间压缩，精准窗口分配最小可编辑宽度。像素参数属于待评审的视觉参数，不是游戏规则。
4. 所有轨道共用 `x(frame)`。同帧控制事件额外用稳定序列呈现先后，不能把序列偏移伪装成经过了时间。
5. 按根施放、效果实例/语义阶段分组，再按显示密度汇总；每组保留所有hitId、首末帧、命中数和累计伤害。首末击、终结重击、状态改变、窗口生成、当前选中命中不能被普通汇总吞掉。
6. 展开效果或放大窗口只更新显示，不重算战斗。拖拽期间冻结投影版本和候选，提交后围绕所选操作重新排布，避免目标在鼠标下跳动。
7. [可独立打开的显示方案](evidence/timeline-ui-20260905/display-prototype.html)使用固定实数结果，演示“重复小伤效果带、窗口聚焦、等时对照”；其宽度分配与聚合阈值仅用于比较方案，尚不是已验收的生产算法。显示数据为[固定快照](evidence/timeline-ui-20260905/visual-cases.json)，不会回写存档。

## 实施顺序与验收

**第一阶段：关系可靠。** 用稳定动作/控制顺序替换像素排序；让 action-end、切人完成、指定命中和窗口依赖进入同一运行时解析链。以保存的F305/306反例验证，不用手填+1掩盖。旧关系锚点需版本化兼容；不能把导入旧存档后的新解析结果静默覆盖原版本。

**第二阶段：事实显示完整。** 修根施放归属、尾部投影，增加效果带。验收F539/547能区分、B①/B②/Q派生不混组、F395末击与F468动作记录结束各自可辨。

**第三阶段：压缩与吸附。** 引入三种视图、无损命中汇总、精准窗局部放大和语义候选菜单。固定同一结果切换视图，动作、资源、命中数、总伤害、接续依赖及同帧顺序完全不变；折叠/展开不触发计算。

**第四阶段：连续操作编辑。** 在原画布与存档工作流中加入接续菜单和可折叠链。验收汤汤Q→切主控→落地，以及卡缪末击→洛茜Q两条完整路径；可展开、修改、撤销、保存、恢复，不要求用户猜多个帧数。

这一轮不包含手机端、引擎增量断点实现或外部游戏机制的全面认证。区分待结算、已执行、被拒绝与机制未验证；不能因执行成功就把未验证门槛改绿。计算期间保留上一结果的版本身份，新的布局不能把预演结果和上一轮结算混为同一事实。性能目标先记录重算、投影、绘制各自耗时，再设预算，不宣称尚未测到的倍数提升。
