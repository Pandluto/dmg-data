# 文档与证据系统

## 目标

文档系统的目标不是“多写”，而是让每个结论只有一个权威落点、每次变化都能复算、每段历史都能追溯。阅读者先从目录理解全局，再按问题下钻到 Spec、架构、证据或维护记录。

## 事实层级

| 问题 | 第一权威 | 冲突时的处置 |
| --- | --- | --- |
| 公开输入是什么 | 原始快照、语料 manifest、`sources.lock.json` | 重新校验哈希；文字不得覆盖机器事实 |
| 系统现在做了什么 | 可执行代码、Schema、运行时 report | 复现实例；架构页随已验证实现更新 |
| 必须做成什么 | Accepted Spec、Accepted ADR | 实现偏离时修实现，或用新决策显式替代合同 |
| 哪些行为已证明 | 测试、fixture/oracle、生成 audit | 按证据等级缩小声明，不用“测试通过”外推 |
| 当前数字是多少 | `docs/evidence/current-snapshot.md` 与其来源 JSON | 运行生成器；禁止手改第二份统计 |
| 为什么发生变化 | 维护记录、Git commit、RIA Session/Run | 当前架构不追加过程日志 |
| 外部项目教会了什么 | research | 只能指导设计，不覆盖本项目证据 |
| 旧材料是什么 | archive、Git history | 只用于追溯，不能参与当前验收 |

需求与事实并不互相替代：Spec 可以要求尚未实现的行为，架构只能写当前已存在的行为，证据只说明当前测量结果。三者状态不同不是矛盾；把它们混在同一段才会制造矛盾。

## 文档类型与唯一责任

| 位置 | 唯一责任 | 禁止内容 |
| --- | --- | --- |
| 根 `AGENTS.md` | 已确认的 Agent 开发约定与条件路由 | 完整实验历史、未经确认的实施授权 |
| 根 `CONTEXT.md` | 项目术语的唯一简明定义 | 源码实现、实验步骤、待办 |
| 根 `H.MD` | 知识库的短入口 | 复制知识正文 |
| 根 `README.md` | 项目定位、最短运行路径、最高层边界 | 完整架构、阶段日志、复制覆盖表 |
| `docs/README.md` | 阅读路由、权威顺序、维护规则 | 实现细节 |
| `docs/specs/` | 用户问题、目标行为、决策、测试与非目标 | 当前统计、提交清单、易漂移行号 |
| `docs/architecture/` | 当前跨模块事实、责任和依赖方向 | 下一步计划、本轮完成日志 |
| `docs/architecture/decisions/` | 难以逆转的跨模块选择 | 普通实现笔记 |
| `docs/evidence/` | 从当前仓库确定性生成的数字证据 | 手工维护统计、原因分析 |
| `docs/testing/` | 可复用验证方法、证据等级与 oracle 口径 | 一次性通过数量 |
| `docs/guides/` | 可以照做的操作、实验、分工与自迭代流程 | 设计争论和历史结论 |
| `docs/knowledge/` | 可路由的术语解释、源码/解包分析与角色结论，附基线、日期和内容提交索引 | 无来源的机制定论、复制当前架构、把旧结论自动视为新版本事实 |
| `docs/research/` | 仍能指导设计的外部对照与机制分类 | 本项目实现完成声明 |
| `docs/maintenance/` | 某次升级、迁移、清理、冲突裁决，以及有证据与状态的探索/提案记录 | 永久架构真相、把待确认提案写成既有合同 |
| `docs/archive/` | 完整保留的退役原文 | 当前入口和验收依据 |

## 生命周期

```text
观察或需求
  → Spec 定义目标与非目标
  → 必要时 ADR 固定跨模块选择
  → 实现与测试
  → 生成证据 / oracle / RIA Run
  → 架构页更新为当前事实
  → 维护记录解释迁移和冲突
  → 被替代材料标记或归档
```

未实现的设计不能提前写成架构事实。已经实现的行为也不能只留在任务或聊天里；它必须进入当前架构并由测试或证据支撑。

## 数据升级事务

一次 AKE 数据升级只有在下列输出共同闭合时才完成：

1. 明确选择 TableCfg version；
2. 显式选择是否刷新 JSON asset revision；
3. 同步表语料和索引范围语料；
4. 从角色、武器、天赋、装备递归发现索引外依赖；
5. 生成逐文件记录、聚合哈希和明确 missing 集合；
6. 重建来源锁；
7. 重生成 analysis、timing 和三类 audit；
8. 运行一致性、根 oracle、跨角色、前端与受影响系统验收；
9. 更新生成证据和带日期的维护记录；
10. 再次运行生成器必须得到稳定结果。

其中任何一项失败都必须保留为错误或已知边界，不能只更新版本号。

## 冲突裁决

| 冲突 | 裁决 |
| --- | --- |
| 架构页与代码不符 | 先用测试/运行复现；代码是当前事实，Spec 决定应修代码还是修文档 |
| 两份当前文档重复且不同 | 确定一个所有者，另一份改为链接或移入维护/档案 |
| 生成报告与手写数字不同 | 重新生成并更新证据页；删除正文中的手写副本 |
| AKE 与 Calc 数值不同 | 保留两种来源和版本，不能互相覆盖 |
| 新数据使旧生成器失败 | 记录失败结构，修生成器的通用边界，再完整重跑 |
| 历史材料与当前结论不同 | 历史保持原文并明确降权；当前结论回写当前事实源 |
| 测试通过但 audit 有 blocker | 声明只限测试覆盖场景，不能写“机制闭合” |

## 可追溯标识

- 公共数据：version、revision、逐文件 SHA-256、语料 content hash。
- 行为证据：fixture ID、oracle 版本、测试名；调查问题再使用 case/session/run/sequence。
- 实现变化：Git commit；工作区未提交状态不能写成既有历史。
- 需求变化：Spec 状态与后继链接；架构决策使用 ADR 编号。
- 当前统计：生成证据页和对应 JSON 路径。

## 文档完成条件

- 新读者能从两层索引定位所需内容；
- 同一事实没有两个手工维护的当前副本；
- 所有相对链接、Spec 结构和生成证据通过自动检查；
- 每个精度声明都能指向对应证据层；
- 所有已知 blocker 明示，未完成不伪装成完成；
- 更新过程有维护记录，历史材料可恢复；
- 按改动完成检查：纯文档验证链接、结构、事实与职责；生成来源变化核对证据新鲜度；业务变化按受影响边界验证，不因文档整理机械重跑业务套件。
