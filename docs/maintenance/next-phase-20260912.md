# 下一阶段：可信接续与可解释的复杂排轴

分析日期：2026-09-12。代码基线：`618921d8449da21cabd2dbafb86fda706b153ac8`（2026-09-12）。
状态：建议，未开始业务实施。本轮只启动现有开发服务器并核对源码、规格和历史实验；不把结构风险写成新复现的 bug。

## 判断

近期已完成宽度压缩、阅读、批量操作和附着归属修正。下一阶段围绕用户的实际问题推进：在某个技能附近接另一个技能，能够知道可接位置、限制原因和后续仍存活的伤害，并在保存、重算、改变显示后保持同一含义。

建议按以下顺序交付，每一步都使用已有 Chrome 工作台与 RIA，不另建演示排轴。

## 1. 让执行顺序脱离画布坐标

2026-09-12 用户已授权本项进入规格与双任务实施，现行施工要求见 [Spec](../specs/timeline-execution-order/spec.md) 和 [详细任务](../specs/timeline-execution-order/tasks.md)。下文保留分析依据；其余阶段尚未随本次授权实施。

当前 [provider](../../demo/lts-ui/src/integrations/ake/akeProvider.ts) 的 `runAkeTeamCalculation` 仍提交 `timelineOrder: action.startX` 与切人的 `change.endX`；[小队 runner](../../src/core/ake-squad-scenario-runner.mjs) 在同帧命令和多个待解析依赖中使用它排序。这条依赖路径已由源码确认。单调压缩未必改变顺序，本次没有证明当前轴因缩放发生伤害变化；风险是执行合同仍依赖视觉布局。

建议以持久化操作身份、队列顺序与显式依赖形成稳定序号，技能和切人共用一套规则。真实因果事件及运行时相位优先，同帧无依赖动作的先后必须有明确规则，不能改成另一种隐含的数组或角色顺序。

旧存档需要显式兼容：冻结旧输入的实际顺序，迁移后保持该顺序；保留迁移版本与原记录。运行时输入身份和显示配置分离，避免只切阅读、换页或改变压缩宽度就让有效执行输入变化。

完成标志：同一冻结轴在不同显示配置及保存重读后，操作顺序、依赖、命中和状态一致；覆盖同帧切人与技能、多个后继共用来源、瞬时施法这几种有实际意义的组合。

## 2. 把“可以接下一招”做成真实关系

现有 [放大镜 Spec](../specs/timeline-release-lens/spec.md) 已明确：`AllowNext` 不是 action-end；新 AllowNext 接点、等待来源的运行时事件和窗口自动重定位尚未纳入首版。当前 `resolveAkeReleaseDependency` 仍按已支持起止/命中/窗口类型转换，终结技命中及拖尾不开放为磁性入口。

先在已有卡缪 Q 案例落地一种有来源的提前接续关系：事件必须说明来源施放、允许的后继类型、有效窗口和时钟。镜面显示“此处可接战技”，与“动作结束后”并列；保存关系身份与偏移，不保存某次预演算出的绝对帧。偏移落到窗口外就明确失败，不悄悄推迟。

显示后果从运行时读取：哪些尚未发生的动作命中被中断，哪些已发射龙卷/投射物继续。现有候选只是接点，不能将每个 DOT tick 自动视作释放许可。未公开或未解析的能力保留未知；不为做出更多菱形而推测角色规则。

完成标志：卡缪 Q 提前接战技与等待实际结束能保存为两种不同意图；汤汤终结技、主控落地及尾伤能说明触发与归属。普攻截段和闪避沿用其已支持边界，再按实际反例扩展。

## 3. 在现有详情里解释一次操作的原因

复用已有事件账本、状态详情和准入提示，整理出一条可读链，例如“战技给予 Buff → 重击触发 → 第三层寒冷生效 → 连携消费”。点开附着可以定位提供动作与触发命中，点开技能可以看到当时的资源、窗口和占用原因。

实际执行状态与规则证据是两个维度：“已释放，但该门槛尚未独立核验”不同于“资源不足，未释放”。[提示聚合](../../demo/lts-ui/src/core/services/akeCombatInspection.ts) 当前先收规划问题，再收运行时失败，且按 commandId 去重；实施时需要检查调用方是否传入同一输入版本，并防止规划结论遮住较新的执行事实。此处是审查目标，尚未复现新的误报。

从局部详情高亮关联的持续效果，主界面继续保持紧凑。暂不铺设全轴效果轨道，也不另造报表。RIA 应返回和详情相同的原因、事件身份、输入版本与来源，不在 UI 再写一套状态推断。

## 4. 用有限实验决定机制与性能工作

以汤汤/别礼和洛茜/卡缪的已归档输入为起点，按一个疑问改变一个因素：

| 疑问 | 有意义的对照 |
| --- | --- |
| 消耗后再次出现的冰从哪来 | 对比新施放生成、旧龙卷延迟命中、施冷标记到期三条因果；不先假定全是错误 |
| 终结技暂停影响什么 | 冻结配装与输入，对比局部技能时钟、全局 Buff 寿命及结束前后一帧 |
| 提前接入会丢哪些伤害 | 可接窗口前/内/外与自然结束，分别核对动作命中和已发出效果 |
| 追加为什么可能改变前面 | 先找新增输入最早能影响的因果时刻，只比较它之前的共同前缀 |

按 [默认配装](../knowledge/experiments/default-loadout.md) 固定六星零潜、五星满潜和装备。当前九动作有四次主动战技，不能作为三战技穷举结果。先解决影响候选可信度的机制，再做明确预算的伤害搜索。

性能先分段记录输入准备、服务端执行、结果传输、投影渲染和归档；首次加载与预热后的连续编辑分开。当前 [历史延迟记录](appended-ultimate-latency-20260905.md) 已证明预热和后台归档带来过改善，但它不是 2026-09-12 的耗时实测。此次 catalog 首次请求约 5.64 秒，仅表示服务启动后的目录准备，不能当作一次排轴重算耗时。

只有战斗重放仍占主要成本时，才推进已有 [前缀续算提案](engine-exploration.md#p-20260905-01从最早受影响位置恢复排轴计算)。首个范围限制为末尾追加、内存内恢复、可回退从头计算；待执行事件、局部时钟、监听、资源与身份必须完整保存。总伤一致不足以验证缓存正确。
